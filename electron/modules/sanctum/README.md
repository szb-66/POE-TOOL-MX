# 圣所开发说明

通过 npm run electron:dev 启动开发版。正式导航未开放，本次不打包。浏览器开发页可核对界面，但没有 Electron 的截图、日志和输入能力，不能用于实机验收。

## 实战策略

新配置默认「揭图收益」，另有「圣物数量速刷」。先满足目标、避让和禁选，再比较明确致命风险、影响玩法的限制、其他未容忍风险、同一路线能兼得的目标奖励、选择空间和用户房型偏好。不同下一房分别列备选。后续路线是条件性预览，实际选择和奖励不会自动提交。

奖励账本及圣物管理已移除，路线不使用装备圣物或已选奖励数据；复制效果仅说明机制，不估算复制收益。

旧 survival/currency/relic 策略加载时整体重置为默认揭图收益，旧权重不再保存。目标优先级可编辑；同种、数量完整的奖励比较可兼得数量，同级不同通货不进行价格换算。未知数量只表示目标机会。

页面依次提供楼层规划、路线策略、识别校准三个同级页签。识别校准保留截图收集、地图、资源和效果配置。

## 实际状态与知识

- 地图确认当前房间即代表完成。首次、跨层或上下文不可信时读取状态栏；同轮同层同地图的可信相邻推进使用此前已读取的房间详情：奖励／宝藏房沿用效果，明确必得痛苦按词条去重加入分类和路线计算。商人、冥约、喷泉、信息缺失及可能在本房间触发的随机、免疫、转换、限次、临时或未知机制效果继续实际扫描。同位置普通观察复用，允许「实际状态 → 手动重读状态栏」强制扫描替换结果。触发判断使用房间事件：毒水侵袭等喷泉效果、购买条件和楼层到期不阻止同层普通宝藏房；转换／额外痛苦只检查新增痛苦，次要痛苦免疫只检查新增次要痛苦。战斗次数、复活、每房随机与倒计时仍重读。进度显示效果名称或上一份状态未完整读取等原因。自动追加保留来源房间和原始截图；触发机制未知时扫描，识别结果保留痛苦身份与计算未知。跳过整个状态栏扫描时，旧奖励保留原观测位置并提示未核对，不推算奖励或复用旧资源；非可信推进的旧效果不参与计算。
- 完整读取替换列表，保留新增、移除、转换和剩余次数变化。部分读取独立保留缺口，不拼接旧列表。路线中的进入/完成效果只用于条件性推演；喷泉、契约等选择不自动获得。
- 位置使用日志上下文和逻辑房间身份，不用屏幕坐标或动画。sanctumRunId 是有连续证据的整轮身份，runId 是采集上下文，captureSessionId 是检测批次。断线、身份回退或无法确认连续性时重新建立身份；重启保存数据仅供历史查看。
- 房间知识分开记录布局、房型、奖励、痛苦、恢复与触发效果。状态含 known、unrevealed、hidden、failed；当前观察或人工修正与旧知识来源不同。默认前方两列是机制对照，不是猜测内容的依据；额外揭示房间数不换算为列数。
- 未揭示节点只用于连通性与选择空间。已真实读取的信息可在同一地图保留；重随机标记、地图身份变化或重新读取冲突后失效。分类隐藏不能让隐藏效果通过另一字段进入推演。
- 已确认连线构成 DAG，汇合后的后续房间去重。互斥奖励组最多选一项，不相容岔路不合并。全部候选有负面仍显示较低风险方案，硬约束冲突不自动放宽；缺失信息与并列明确显示。

## 资源与奖励读取

楼层规划内的实际状态提供坚毅、最大坚毅、启迪和耀金币。资源绑定当前逻辑位置；人工保存时核验位置，迟到结果不应用。没有实际资源或费用时不计喷泉恢复；满坚毅、无法恢复、金币不足时不加分。

在「策略与校准 → 状态栏」配置地图内金币图标与数量、坚毅启迪完整模块，以及地图外完整状态栏。完整识别自动刷新可见布局的资源，效果缓存沿用也会刷新；单独读取按钮支持两种布局。金币图标及右侧数字定位余额（270(+0) 只取 270），坚毅启迪按文字标签和位置识别；只有单行模块完整边框与坚毅居中证据确认时，无启迪才记为 0。未配置、遮挡或 OCR 失败保持未知。v6 保留地图金币及其他有效配置，旧坚毅启迪小框不拼接，请重新框选完整模块并留少量边距。

在有效圣所采集会话中，地图关闭后独立状态栏自动显示，无需校准独立状态栏识别锚点；旧锚点配置不参与采集。地图内状态栏仍使用自身锚点，效果图标范围和资源区域分别保留，地图关闭不代表扫描完整或没有效果。

独立状态栏读取结束后，系统搜索并点击已校准的「禁域地图」文字入口，确认地图打开；缺失、多匹配、环境失配及开启超时明确报告，不回退按 V 开启。关闭仍按 V，开始识别时不会额外重开地图。

状态栏奖励提示只作分类排除，防止被误判为恩赐痛苦；不提取已选奖励数据。房间奖励图标与选项继续识别并参与路线推荐。

每次完成地图采集保存最近 20 次决策时的可知地图、效果、资源、策略和推荐；下一次实际房间变化只核对选房结果，不推算领奖。gameplayAccepted 始终默认为 false，自动记录不代表人工实机验收通过。

## 来源、规则和识别边界

- 原项目 [Exile-UI 圣所规划器](https://github.com/Lailloken/Exile-UI/wiki/Sanctum-and-Sekhema-Planner)提供逐步标记/可达节点思路；[原 AHK 实现](https://github.com/Lailloken/Exile-UI/blob/main/modules/sanctum.ahk)没有可直接当作这套自动实战收益策略的固定权重。
- [PoE Vault 机制](https://www.poe-vault.com/guides/the-forbidden-sanctum-league-mechanic)、[生存与选路](https://www.poe-vault.com/guides/the-forbidden-sanctum-league-mechanic-surviving-the-sanctum)用于区分可选喷泉/契约、奖励选项及后续选择空间；历史价格不作为当前行情。
- [编年史圣所](https://poedb.tw/cn/Sanctum_league)、[遗物](https://poedb.tw/cn/Relics)、[神圣之刻](https://poedb.tw/us/The_Hour_of_Divinity)提供原文、物品条件和奖励目录。新增解析使用现有奖励目录，不限于神圣/混沌/崇高；只有图标时不赋数量。
- catalogReviews.json 的内容指纹与赛季核对独立于名称识别。123个恩赐/痛苦条目及次数变体由共享规则注册表和路径事件评估器处理：确定性事件推演资源，战斗、随机和购买条件进入风险或机会排序。当前资源已包含持有效果，获取时变化不重复扣减；未审核或数字不符的文本仍保留缺口。不能因为 OCR 选中了最高相似词条就宣称规则实现完整。
- 国服房型与公开布局对照仅用房间名称映射；同名多候选不能统一时保留未知，不估算未知房型耗时。实际地图和弹框样本来源见 test/fixtures/sanctum/supplied-samples.json；模板版权与来源见 src/assets/sanctum/README.md。

目录生成使用 npm run sanctum:data（已有缓存离线生成）或 npm run sanctum:data:refresh（显式刷新来源）。运行中不联网下载规则。刷新来源变化使内容审核失效，不自动升级为已验证。

### 效果识别与截图核对
入口图标只用于悬停。浮窗名称和描述匹配词库后取得恩赐/痛苦及主要/次要分类，不要求类别标题。识别缺口和计算条件分别展示；扫描结束仍无法确认的类别显示“读取失败”，完整扫描确认不存在才显示“无”。推荐区列出失败目标、阶段、原因和重读入口，历史路线保留保存时的缺口。
每个房间和状态浮窗保存最近一次处理后的裁剪图及对应原文，图片存入用户数据目录的 sanctum-images，内存淘汰不删除持久图片。新图落盘并原子保存结果后清理旧图；采集失败保留旧图和原文并标注“上次采集”。重启可查看，重置记录清理本轮图片，但保留长期纠正规则及版本记录引用的原始截图。旧版没有图片的存档显示“未保存截图”。历史全图仍可查看，新增采集仅保存处理后的裁剪图。
状态区域固定提供“管理已记住的纠正”，已读效果仍有核对入口。核对默认将明确原文到词条或忽略的处理保存在本机 effectCorrectionMemory，取消勾选仅作用本次；无原文的额外添加不创建记忆。匹配只统一全半角和空白，保留数字与标点，按完整来源精确复用，不跨奖励行或递归套用。规则可搜索、修改、删除；修改从原始 OCR 更新当前效果及路线，历史结果不改写。词库目标描述或级别变化时停用规则；截图失败、覆盖不足及计算未支持仍保留原因。
独立状态栏普通失败后检查实际界面并尝试恢复地图，停止或环境失效后不再按键。主进程和 preload 修改需要重启 Electron 开发版生效；不打包。

### 识别性能回放

`node scripts/sanctum/benchmarkRecognition.mjs --mode=compare --runs=5 --baseline-ref=<提交>` 使用固定裁剪图通过实际驱动与真实 Python 工作进程对照，`--scenario=rewards` 测奖励密集输入，`--mode=matrix` 比较工作进程和 OCR 线程配置。报告保存到 `.cache/sanctum-speed/benchmark.json`，识别事实不一致或出现失败时以非零状态退出。它不控制游戏，不能替代实机整轮验收；实现记录见 OpenSpec 的 `archive/2026-09-13-accelerate-sanctum-recognition/verification.md`。

后台文字与图标通道独立，图标扫描保持全部模板及评分规则并有限并行。已解码的房间图片通过带会话/目标/帧身份的内存引用供图标使用，最多八个待完成房间任务及 128 MiB 解码图片；引用不进入用户存档。必要图标结束前按钮不会提前完成。

完整状态评估与图片持久化的验收记录见 openspec/changes/archive/2026-09-11-complete-sanctum-state-evaluation/verification.md。

## 房间玩法与推荐

房间标题与正文由一次 OCR 分区输出，标题仅匹配有来源的四层名称目录。实机标题同时列出四层对应名称时，要求全部候选可核实且包含当前楼层，只采用共同属性。名称、通关目标、已知陷阱与奖励功能分别保存；未列陷阱不代表无陷阱，小首领与楼层首领分开。

揭图收益在选择空间之后比较房型，圣物数量速刷在同等奖励与主要风险下先比较房型；依次比较下一间偏好和后续已知偏好合计。偏好在逐房推演时保存，后续隐藏不反向改写前面房间。详情显示来源，修正名称或玩法清除旧属性。

### 前台采集性能

150ms 悬停等待保持不变。截图只受原始帧及待识别图片缓冲容量限制，不再绑定八个完整房间任务；原始帧沿用 512MiB 上限，待识别 PNG 为 128MiB / 128 项，已解码图像为 128MiB / 8 项。后处理输出获得预算后释放原始帧，OCR 后释放 PNG，必要图标完成后释放解码图像。

资源截图与资源 OCR 分离，布局与效果图标定位复用同一有效帧。截图采集结束可释放鼠标，界面完成仍等待资源、房间、效果及图标处理。采集通道只在首次配置传递静态标题和校准，动态目标、身份、截止时间及窗口检查逐次保留。

成功完整识别后，OCR 和图标进程保温最多 60 秒，图片与采集进程立即释放。超时、失败、停止、过期或退出不得复用模型进程。打开新采集时更换采集会话和图像队列，保温进程仅保留静态模型/模板。

`captureMetrics` 新增 `prepareStages`、`warmWorkers`、`clickToFirstMoveMs`、`moves`（原生单调时钟的相邻移动间隔）、`effectsCaptureMs`、`effectsTotalMs`、`resources`（截图、队列、识别和总耗时）。首移时间以主进程收到实际移动事件为准，包含事件传输耗时。各阶段会重叠，不应相加作为整轮耗时。

`node scripts/sanctum/benchmarkForeground.mjs --mode=startup --runs=5` 使用本轮本地基线对照四类真实工作进程的就绪耗时，不操作游戏输入，也不属于实机采集验收。基线位于 `.cache/sanctum-speed/foreground-baseline`，含修改前代码与 SHA256 清单；清单摘要和启动数据保存在本变更的 `foreground-performance.json`。此启动测试固定解释器，不包含依赖探测或游戏激活；不得把它称为应用冷启动成绩。

实机验收使用 `node scripts/sanctum/benchmarkForeground.mjs --mode=live --input=<records.json> --output=<report.json>`。输入为按实际采集顺序排列的数组，每条含 `version`（baseline/current）、`scenario`（cold/continuous/rewards/effects）、`pair`、`live:true`、`loadComparable:true`、`environment:{machine,scene,width,height,dpi}`、冷启动场景的 `appCold:true`、经样本人工核对的 `accuracy`、`failures`，以及该轮 `captureMetrics` 作为 `metrics`。每对相邻记录的机器、场景与分辨率须相同；每场景至少五对。准确率、负载确认与实机标记必须来自实际验证，不由脚本推断。报告分别列中位数、P95、鼠标占用、准确率与失败数；缺数据、退化或不足 50% 返回非零退出码。原始整轮 50% 验收仍单独保留。
