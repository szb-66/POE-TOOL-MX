## Context

`openspec validate --all --strict` 会把主规格 Purpose 少于 50 个字符视为严格校验失败。当前仓库有 33 个历史主规格触发该规则，其中部分 Purpose 是 `TBD`，其余仅有一句过短概述。每份规格的 Requirements 和 Scenarios 已经提供了足够的领域语义，可以作为重写 Purpose 的权威依据。

本变更横跨多个能力规格，但只涉及文档元数据。实施时必须保护既有需求正文，并避免用同一段通用文本机械填充所有能力。

## Goals / Non-Goals

**Goals:**

- 消除全仓严格校验报告的全部 Purpose 过短警告。
- 让每份修复后的 Purpose 准确概括该能力覆盖的主要行为与边界。
- 保证修改范围仅限目标规格的 Purpose 内容。
- 让 `openspec validate --all --strict` 最终以零警告、零错误退出。

**Non-Goals:**

- 不新增、修改、删除或重命名任何 Requirement 或 Scenario。
- 不调整运行时代码、测试代码、依赖或构建配置。
- 不借本变更处理与 Purpose 长度无关的文档重构。

## Decisions

### 以严格校验 JSON 输出作为目标清单

先运行全仓严格校验并从结果中提取 `overview` 路径的 Purpose 过短警告，只修改该清单对应的主规格。相比扫描短文本，这能确保目标集合与实际门禁完全一致，也避免误改不受影响的规格。

### 从现有需求正文归纳能力用途

逐份读取目标规格的 Requirement 标题和场景，编写能够覆盖主要职责、输入输出或安全边界的 Purpose。不会通过重复能力名称或填充无意义字符来满足长度阈值，因为这会通过校验却降低规格质量。

### 将编辑限制在 Purpose 与 Requirements 之间

每个文件只替换 `## Purpose` 和 `## Requirements` 之间的正文。实施后检查差异，确认 Requirement 与 Scenario 行没有变化。相比整文件格式化或批量重写，这种边界能最大限度降低行为契约被意外修改的风险。

### 使用全仓严格校验作为唯一完成门禁

定向校验只用于快速定位问题；最终必须执行 `openspec validate --all --strict` 并确认退出码为 0、失败数为 0、警告数为 0。这样可以捕获修复过程中引入的其他规格问题。

## Risks / Trade-offs

- [Purpose 虽满足长度但与需求不一致] → 每项说明均从同文件的 Requirement 标题和场景归纳，并在修改后抽查差异。
- [批量编辑误触需求正文] → 限定替换区间，使用 `git diff` 和 Requirement/Scenario 行对比进行审计。
- [校验目标在实施期间发生变化] → 修改前后都重新运行全仓严格校验，以最终输出为准处理新增或残留警告。
- [历史规格语言不统一] → Purpose 优先沿用该规格正文的主要语言，但不为了统一语言扩大修改范围。

## Migration Plan

1. 记录全仓严格校验的当前失败清单。
2. 逐项更新目标主规格的 Purpose。
3. 运行全仓严格校验并处理任何残留警告。
4. 审计差异，确认需求正文未改变。

如需回滚，只需恢复本变更对各主规格 Purpose 段落的修改；运行时代码和数据无需迁移。

## Open Questions

无。完成条件和修改边界均由现有校验规则及规格内容明确给出。
