## Context

普通仓库和君锋镇共用 `junfeng_highlight_pickup.py` 的候选处理循环与背包脚本提供的 `InputController`。当前共享转移函数只发送一次点击，取件调用方随后直接增加 `pickedItems`；主规格也明确禁止点击后复制，因此背包已满时没有停止信号。

## Goals / Non-Goals

**Goals:**

- 在普通仓库和君锋镇唯一的共用取件路径实现最多三轮点击后复制确认。
- 任一轮确认清空后立即结束重试，三轮仍有物品时稳定产生 `inventory-full`。
- 保持背包入库的单次点击语义以及现有输入安全边界。

**Non-Goals:**

- 不扫描背包、不计算物品尺寸，也不新增次数或时序配置。
- 不区分背包已满、游戏卡顿和连续输入丢失；三次仍有物品统一按背包已满处理。

## Decisions

### 1. 在共享输入模块增加取件专用确认函数

保留 `transfer_item_once` 给背包入库使用，新增取件专用函数封装固定三轮 `ctrl_click` 与 `copy_item_text`。普通仓库和君锋镇已经共用同一运行循环，只需一个调用点即可保持行为一致。

不直接改写 `transfer_item_once`，因为这会让背包入库也执行点击后确认并改变已归档的入库安全语义。

### 2. 复制状态决定重试和停止原因

每次点击成功发出后立即调用现有剪贴板复制能力。`empty` 表示来源格已清空并成功；`copied` 表示物品仍在，前两轮继续、第三轮返回 `inventory-full`；其他状态返回当前前台原因或 `transfer-unconfirmed`，不得继续点击。

### 3. 成功确认后提交统计

调用方只在确认函数成功后增加 `pickedItems`。失败事件继续携带当前候选和剩余数量，现有管理器与浮窗已支持 `inventory-full` 文案，无需新增 IPC 或 UI 分支。

## Risks / Trade-offs

- [游戏连续卡顿或三次输入丢失被误判为满包] → 接受用户选择的简化规则，并严格限制为三次，禁止第四次点击。
- [点击后复制过早读到旧物品] → 复用现有点击释放等待和剪贴板确认窗口，不增加另一套时序。
- [共享模块误改入库行为] → 保留单次入库函数，并分别运行入库和两种取件契约测试。

## Migration Plan

1. 先用行为测试覆盖第一、第二、第三轮成功及三轮失败。
2. 增加取件专用确认函数并替换共用取件循环的单次调用。
3. 删除与“点击后不复制、单次点击即成功”绑定的冲突测试和无效状态文案断言。
4. 运行相关测试、完整测试和 OpenSpec 严格校验；仅在开发版手动验证，不打包。
