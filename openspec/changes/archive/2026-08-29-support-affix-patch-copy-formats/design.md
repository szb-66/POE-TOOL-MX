# 设计：支持词缀补丁复制格式

## Context

所有剪贴板物品文本（查价、制作、文件导入）都经过 `electron/modules/item/parser.js` 的 `parseItemInfo` 单点解析。词缀头在 `parseItemInfo` 内识别（`前缀属性/后缀属性` 等固定措辞），词缀行经 `cleanModifierLine` 清洗（目前仅剥数值区间）后进入 `modifiers/explicitMods` 等结构化字段。查价侧 `resolveCatalogStat` 依赖清洗后的文本与官方目录精确锚定匹配，因此解析输出契约不变时下游零改动。

已用真实补丁复制样本复现失败：词缀头不被识别 → 词缀分组为空，带区间原始行漏入 `explicitMods`。见 proposal.md 的 Why。

## Goals / Non-Goals

**Goals:**
- 功能补丁（T0）与简改词缀 v1/v2/v3（T1-T3）的装备复制文本解析正确：词缀分组、等阶、标签、清洗后的可匹配文本与官方格式一致
- 官方格式（无补丁、原版词缀补丁）行为完全不变
- 回归样例与测试锁定新格式

**Non-Goals:**
- 不建立国际服→国服词缀文案别名映射（T0 改写文案接受"未映射词缀"降级，用户已确认）
- 不处理 `W`（白色插槽）颜色统计——不计颜色但计入总孔数与连接数，对查价无影响
- 不改动查价、制作、匹配等下游模块

## Decisions

1. **只改解析器单点，不动下游**
   `parseItemInfo` 是全部剪贴板文本的必经收口点；在源头保证输出契约（清洗后的行文本 + 结构化 modifiers）与官方格式一致后，查价/制作自动受益。
   备选：在各下游模块兼容新格式——改动面大且遗漏风险高，放弃。

2. **词缀头正则用 `(?:属性|词缀)` 双措辞扩展，而非新增分支**
   现有代码已有先例：`基底(?:属性|词缀)`。对 affixType（前缀/后缀）与 semanticType 词表（工艺、附魔、隐式、传奇、隐匿、灾魇）统一照此扩展；`▲/▽` 标记与 `（上级L3）` 等阶写法位于头行内，无需单独解析（等阶正则 `等阶[：:]` 已兼容全角冒号；焚界/灭界头本就整行归类，等阶不参与匹配）。

3. **装饰剥除放进 `cleanModifierLine`，顺序：先尾注后区间**
   - 行首 `▲/▽ ` 标记（简改 v1）：`^[▲▽]\s*`
   - 行尾连续 `[...]` 注释组（功能补丁）：`(?:\s*\[[^\]]*\])+\s*$`
   - 之后走现有区间清洗。
   `cleanModifierLine` 是所有结构化词缀行与单行 enchant/fractured 词缀的共用清洗器，在此剥除可同时覆盖分组行与独立行。
   备选：仅在词缀分组循环内剥——会漏掉 `(enchant)/(fractured)` 单行路径，且逻辑分散，放弃。

4. **回归样例取 T2 文案，T0/T1 变体走专项单测**
   `priceCheck.test.js` 的全样例循环断言"每条词缀都能映射到官方候选"，T2/T3 为官方文案可通过；T0 含改写文案必然产生无候选的未映射词缀，T1 与 T2 解析应完全等价。因此：真实 T2 样例进 `supportedItemFormats.js` 示例表（自动纳入两个测试循环）；T1/T0 用测试内联文本断言清洗与分组结果。

## Risks / Trade-offs

- [行尾 `[...]` 剥除可能误伤理论上以方括号结尾的官方词缀] → 国服官方词缀数值用圆括号区间、无行尾方括号用法；剥除仅限行尾且匹配现有测试全量回归兜底
- [T0 改写文案词缀无法自动生成查价过滤器] → 已确认为可接受降级；UI 现有"未映射词缀"提示兜底，查询主体（底材身份）不受影响
- [补丁版本继续演化出新措辞] → 正则按措辞族（属性/词缀）而非逐字面扩展，样本出现新变体时补样例即可

## Migration Plan

纯解析兼容性扩展，无数据迁移。发布后旧官方格式与新旧补丁格式并存可用；如需回滚仅还原 `parser.js` 三处正则与两行清洗逻辑。
