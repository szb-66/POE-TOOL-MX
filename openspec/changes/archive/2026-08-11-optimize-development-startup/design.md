## Context

现有入口在 `router.isReady()` 后挂载 Vue，正确避免了浮窗误执行主窗口初始化；但根组件静态导入大量业务 Store 和服务，首页又直接依赖多数领域模块，导致 Vite 冷启动形成约 140 个资源的转换瀑布。已有 `renderer-mounted` 同时承担启动日志和 CrashGuard 边界，必须保留其安全语义。

## Goals / Non-Goals

**Goals:**

- 用可重复、结构化的开发版基准约束外壳和首页就绪时间。
- 在保持初始路由判定的前提下缩小首次挂载静态依赖图。
- 让业务运行时部分失败可观察、可清理且不阻塞界面。

**Non-Goals:**

- 不预加载全部业务页面，不改变 HMR、端口或 LocalStorage origin。
- 不改变业务配置、运行规则和打包流程。
- 不用全量 Element Plus CSS 替代现有按需样式。

## Decisions

### 1. 保留路由就绪门禁，缩轻门禁两侧的依赖

继续在挂载前等待 `router.isReady()`，因为浮窗与主窗口共用入口，提前挂载会让初始 `route.meta` 尚未解析时短暂执行主窗口初始化。优化通过轻量首页外壳和动态主运行时实现，而不是删除安全门禁。

### 2. `renderer-mounted` 保持唯一 CrashGuard 边界

根应用与轻量初始路由外壳挂载后继续上报 `renderer-mounted`。新增 `dashboard-ready` 和 `renderer-runtime-ready` 只用于性能与故障定位；首页异步内容由页内错误边界恢复，因此其失败不升级为整个渲染器不可恢复。

### 3. 主窗口运行时采用单例 Promise 和统一 disposer

动态模块注册监听器后再同步状态，初始化入口复用同一个 Promise，卸载复用同一个清理集合。游戏标题和进程名保持串行同步，之后的 DPI、快捷键、战斗与各业务运行时按子系统并行执行并各自捕获错误。

### 4. 首页路由模块只包含外壳

首页外壳使用异步组件加载现有业务内容，fallback 保留分区结构，错误态支持重试。其他页面仍维持现有按意图预加载，不在启动期批量预取。

### 5. 基准使用诊断事件而不是视觉猜测

启动器和主进程输出脱敏 JSONL 事件，基准进程按本轮 run id 采集阶段并计算中位数。冷启动使用新的 Vite 进程与空转换内存缓存，热启动复用 Vite 服务；只清理本次启动的子进程和临时报告。

### 6. Vite 只预热首屏闭包

`server.warmup.clientFiles` 限定入口、主布局和首页外壳，`optimizeDeps.include` 固定框架依赖，watch 排除运行时、构建输出、原始数据和训练输出。这样减少转换瀑布和目录扫描，又不会牺牲业务页面懒加载。

## Risks / Trade-offs

- [监听器延后注册可能漏掉早期事件] → 动态运行时先注册监听器，再通过状态查询进行对账。
- [首页异步内容失败后 CrashGuard 已完成] → 页内错误边界保留导航并提供显式重试，同时记录受限失败事件。
- [固定秒数受机器负载影响] → 同时验收三次中位数和相对基线，报告保留每轮原始阶段数据。
- [预热范围再次膨胀] → 只允许轻量首屏文件进入 warmup，并以资源数量和基准回归测试约束。

## Migration Plan

无需数据迁移。先落地诊断和基准，再拆运行时与首页，最后配置 Vite；每一步均可用同一基准比较。回滚时恢复根组件直接初始化和首页同步组件，新增诊断事件可独立保留且不影响旧日志读取。
