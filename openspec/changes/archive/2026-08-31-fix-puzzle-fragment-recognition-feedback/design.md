## Context

见 `proposal.md`。当前词缀匹配器先将范围替换为占位，再替换剩余数字，因此 `3(2-4)` 产生两个占位而目录 `(2-4)` 只有一个。仓库格子已经独立持有形状与 `mods` 状态，但未知词缀只出现在悬停首行。识别服务还在发布结果和 `finally` 中多次触发同步 `show/focus`，既未确认 Windows 实际焦点，也使“是否执行过自动化”的边界不清晰。

## Goals / Non-Goals

**Goals:**
- 在共享匹配入口修复实际掷值加范围的结构化归一化，避免为单个词缀写特例。
- 让形状未知与词缀未知在同一格子中拥有互不混淆的视觉语义。
- 将结束聚焦收敛到可等待、可验证、可补偿的一条路径，并保持前置校验安全边界。
- 在大量既有未提交改动中使用小范围补丁，不覆盖当前海图校准和边缘编辑工作。

**Non-Goals:**
- 不放宽目录匹配阈值，不对任意双数字进行猜测性合并。
- 不改变词缀目录、状态枚举、持久化、IPC 或求解器。
- 不新增后台常驻聚焦、窗口轮询、打包或发布流程。

## Decisions

### 在数值占位前折叠“当前值 + 范围”
共享规范化先识别“一个数值紧邻一个括号范围”的有限结构，仅移除范围前重复展示的当前值，再沿用原有全角转换、范围占位和数字占位。这样 `3(2-4)` 与 `(2-4)` 产生同一结构，同时 `2 秒内出现 3 个怪物` 仍保留两个数字位置。相比在目录中补充每个实际值变体，该方案覆盖所有稀有海图词缀且不扩大词缀目录。

### 用独立“词?”角标表达词缀未知
仅当格子已有有效形状且 `mods.status === 'unknown'` 时显示“词?”；未知形状继续使用现有中央问号，`unveiled` 不视为未知词缀。角标使用独立位置和类名，避免与方案编号、方向角度、锁定及本机校准标识复用状态。悬停继续以现有 `fragmentModTooltipLines` 展示原文。

### 结果文案复用现有统计但明确对象
不新增统计字段，继续由 `fragmentProbe.unknown` 驱动部分成功，只将碎片结果文案从“未知 N 个”改为“词缀未知 N 个”。格子角标直接读取持久化后的单格 `mods.status`，两者共享服务端识别结果而不是在页面重新推断。

### 聚焦恢复异步验证并至多补偿一次
窗口管理器提供可等待的恢复结果：先恢复已有最小化状态、显示、移到顶层并聚焦；下一事件循环检查 `isFocused()`。实机验证表明，主窗口可见但被游戏遮挡时，Windows 仍可能拒绝 `show/focus` 与临时置顶，而坐标取点流程通过最小化后的 `restore()` 可以可靠获得前台。因此首次恢复失败后，补偿步骤对仍可用且未最小化的主窗口执行一次最小化，再立即恢复、显示、移顶和聚焦，并再次检查实际焦点。该方案复用 Electron 现有窗口能力，有确定上限、不新增依赖，也不改变用户常驻置顶设置。

### 服务记录是否真正进入自动化
碎片识别仅在即将调用分析子进程前标记已执行自动化，边缘识别在获得锁并启动运行反馈后进入自动化路径。结果发布只发送数据，不再隐式抢焦点；服务在最终结果和子进程均结束后统一等待窗口恢复。这样部分成功与其他终态共用同一路径，而区域、页签、繁忙和锁校验失败不会改变前台窗口。

## Risks / Trade-offs

- [部分国服文本在当前值与范围之间带空格或全角连接符] → 折叠逻辑允许空白并复用现有半角转换，使用完整样本和变体测试覆盖。
- [最小化恢复补偿可能产生短暂视觉闪动] → 仅在首次聚焦被系统拒绝时执行一次，并在同一补偿步骤立即恢复、显示和聚焦；以开发版人工验收确认。
- [未知角标与已有角标重叠] → 为“词?”保留单独定位并用页面结构测试锁定所有标识同时存在。
- [工作区相关文件已有未提交改动] → 每次补丁前后检查局部 diff，只修改目标片段，不格式化整文件。

## Migration Plan

无需数据迁移。先运行定向测试、完整测试、Vite 开发构建和 OpenSpec 严格校验，再在当前开发版完成稀有格式与真实未知格式两轮人工验收。出现回归时可独立回退本变更的匹配、角标和聚焦补偿片段，不影响已有持久化数据。
