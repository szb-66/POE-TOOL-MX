## Context

现有诊断由首页提交八个模块的状态，主进程补充系统、显示器、Python 和游戏 DPI 后直接写出 JSON。只有运行时和 DPI 错误会经过有限正则脱敏，项目没有持久应用日志；现有事件错误分散在渲染层服务和主进程服务中。

## Goals / Non-Goals

**Goals:**
- 让导出文件在不包含用户内容的前提下回答“什么环境、哪个模块、何时以什么原因失败”。
- 让重启前的近期失败仍可导出，并确保事件存储自身故障不影响业务。
- 将所有进入诊断的渲染进程输入和自由文本视为不可信数据。

**Non-Goals:**
- 不采集原始日志、截图、配置、物品、仓库、账号、URL 或请求响应。
- 不自动上传，不引入服务端、第三方依赖、ZIP 或持久设备身份。
- 不在本变更中执行安装包构建。

## Decisions

1. **单个 schema v2 JSON 作为支持契约。** 顶层保留环境快照并新增 `diagnosticId`、`health`、模块 `reasonCode` 与 `recentEvents`。随机诊断 ID 每次生成，事件按每次应用启动的随机会话 ID 分组。相比 ZIP，JSON 更便于用户人工检查。
2. **最终对象递归脱敏并结合字段白名单。** 所有外部载荷先按允许的 ID、状态、原因码和数值元数据重建，再在序列化前递归处理字符串。相比依赖正则清洗任意日志，固定结构从源头降低泄漏面。
3. **使用小型 JSON 事件账本。** 账本位于用户数据目录的 diagnostics 子目录，最多 200 条。写操作以 Promise 队列串行，写临时文件后 rename；每次读写裁剪 7 天历史。短时重复事件更新最后一条的时间与计数，避免故障循环放大文件。
4. **只记录失败与恢复。** 受支持入口调用统一记录 API，失败文本经集中分类器映射成固定原因码；无法分类时使用 `unknown_failure`。成功只在同一操作存在未恢复失败时记录 `recovered`，避免记录行为轨迹。
5. **主进程强制事件枚举。** 事件模块、操作、结果、原因码和元数据键均由主进程白名单过滤。渲染层可报告受支持事件，但不能写自由文本。系统健康在主进程直接记录。
6. **导出流程可注入测试依赖。** 将保存对话框、快照生成、事件读取和文件写入组合为可单测函数；先显示对话框，取消时不运行探测。失败统一返回固定错误码与安全提示。

## Risks / Trade-offs

- [固定原因码缺少原始堆栈细节] → 保留覆盖主要故障类别的集中映射，未知情况仍能通过模块、操作、版本与环境定位。
- [高频事件写盘] → 仅写失败/恢复、60 秒去重并串行写入。
- [旧事件文件在升级后格式变化] → 事件文件自身带版本；不支持或损坏时忽略并在下次写入重建。
- [正则无法识别无上下文的随机秘密] → 不导出任意日志或业务文本，递归脱敏只作为白名单后的纵深防御。

## Migration Plan

- schema 从 1 升至 2；现有事件文件不存在时按空历史处理，无用户数据迁移。
- 发布前在开发版导出并人工审查；若出现回归，可回退导出 v2 与事件记录代码，事件文件不被其他功能读取。
