## Context

当前 Electron 服务从国服仓库接口归一化物品，只保留混沌套装需要的稀有度、物等、鉴定状态和装备部位。引擎直接过滤 60 级以上稀有装备，快照和 IPC 也只暴露一个混沌套装结果。坐标、高亮、自动取件、暂停继续和界面检测已经是可复用的稳定链路。

## Goals / Non-Goals

**Goals:**

- 使用统一物品池同时计算七种配方，并按用户选择创建单一配方的安全取件计划。
- 复用现有完整套装优化器、跨页坐标、高亮和自动取件链路。
- 保持旧 IPC 通道、本地设置和混沌快照字段兼容。
- 在物品冲突时保护收益更高或用途更专一的配方。

**Non-Goals:**

- 不支持特殊仓库布局、品质三倍奖励或其他商店配方。
- 不自动点击商人确认交易，不根据市场价格决定是否出售。
- 不跨刷新保存单件候选勾选状态。

## Decisions

1. 快照以完整 `items` 物品池为源，`recipes` 保存每个配方的派生结果。旧混沌顶层字段映射到 `recipes.chaos`，而不是维护第二套计算。
2. 完整套装使用共享的部位分配器和配方策略。机会、混沌、富豪由物等谓词区分；崇高按六种经典势力分别求解，并保证多势力物品在最终集合中不重复。
3. 插槽配方先按链结、六孔、三色顺序唯一分类。所有插槽候选从完整套装池剔除；所有经典势力装备只进入崇高池。
4. 取件接口保留现有 IPC 名称，计划请求扩展为 `recipeId`、`setCount`、`itemIds` 和 `calibration`。套装忽略 `itemIds`，单件忽略 `setCount`。
5. 页面刷新后为每个单件配方默认选择全部候选，当前选择只保存在 Pinia 运行态。`activeRecipeId` 持久化，非法旧值回退为 `chaos`。
6. Python 校验配置携带配方类型和期望插槽签名。套装继续验证稀有度与物等；单件允许任意稀有度并验证中英文剪贴板插槽文本。

## Risks / Trade-offs

- [国服旧接口可能缺少插槽或势力字段] → 缺失字段安全归一化为空并计入诊断，不猜测配方。
- [双势力物品导致重复计算] → 崇高求解器在选定集合层面维护已使用 ID，并用稳定顺序选择最大套数。
- [单件默认全选可能误卖贵重物品] → 页面必须展示名称、底材、位置和产出并允许取件前取消；脚本逐件验证身份和插槽。
- [不同配方预览共享同一物品] → UI 明示统计不可相加；每次只运行一个配方，逐件消费后重算全部结果。
- [兼容字段造成短期重复接口] → 旧顶层字段仅作为 `recipes.chaos` 的浅映射，后续独立变更再移除。

## Migration Plan

1. 先扩展归一化和纯函数引擎并保持旧输出。
2. 扩展服务、IPC、自动取件配置和浮窗状态。
3. 迁移 Store 和页面；旧设置默认选中混沌配方。
4. 完成全量测试后发布。回滚时旧 IPC 与旧设置仍可由原混沌路径读取。
