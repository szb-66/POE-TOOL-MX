## Context

见 `proposal.md`。当前海图识别由 Electron 主进程组织双页流程，Python 识别器完成截图、网格定位和碎片分析；诊断由主进程生成单个脱敏 JSON，反馈服务把该 JSON 作为一个系统诊断附件上传。现有事件只能说明最终错误，且主规范明确排除仓库内容，因此无法从已提交反馈复盘真实识别画面。

本变更跨越 Python 识别器、主进程海图服务、临时文件生命周期、诊断导出和反馈附件组装。现有公开 IPC、识别返回结构和自动化安全门禁必须保持不变，失败证据采集也不能使识别操作失败或增加输入动作。

## Goals / Non-Goals

**Goals:**

- 让一次最终失败的海图碎片识别可以离线还原每次截图尝试的完整游戏窗口、实际裁剪内容和网格检测过程。
- 使证据在本地具有确定的替换、过期、提交成功清理和提交失败保留语义。
- 在既有反馈总容量、CloudBase Storage 访问控制和用户明确附带诊断的边界内上传证据。
- 保持识别业务结果与诊断采集故障隔离，并可通过开发版自动化测试验证。

**Non-Goals:**

- 不修改绿色碎片阈值、网格算法、双页点击策略、自动放入或求解逻辑。
- 不将普通桌面、其他模块画面或持续录屏纳入诊断。
- 不在本变更中判断 FB-20260825-4C3DED9A 的真实根因，也不把证据采集本身作为该问题的修复。
- 不制作安装包、不发布版本、不改变公开 IPC 和云端反馈数据表结构。

## Decisions

### 1. Python 在同一次截图后派生完整窗口与裁剪证据

识别器在每次只读截图尝试中使用同一时刻的游戏窗口图像派生配置区域裁剪，避免“完整窗口”和“实际识别输入”来自不同时间。游戏窗口边界来自已验证的前台游戏句柄，并与显示器物理边界求交；无法得到可信边界时只记录缺失原因，不退化为全桌面截图。

选择该方案是因为根因分析需要证明识别器当时真正看到的内容。由 Electron 事后再次截图会产生时间差，单独保存配置区域又无法判断坐标偏移。替代方案“只增加等待和重试日志”无法区分截图错位、画面未稳定和网格算法失配，因此不采用。

### 2. 识别器输出内部证据清单，主进程剥离后再返回渲染层

Python 内部结果增加仅供主进程消费的证据描述，包括随机工作目录、尝试指标和文件元数据。海图服务在形成现有渲染结果前剥离这些字段，将最终失败证据交给独立仓库保存；成功、停止或非实时图片分析清理本次工作目录。

这样可以避免改变公开 IPC 数据结构或把完整路径暴露给渲染进程。替代方案“把路径加入现有识别结果”会扩大可见契约和敏感路径暴露面，因此不采用。

### 3. 使用原子目录保存最近一次证据

在应用 `userData` 下建立专用诊断证据目录，以随机标识命名暂存目录并在所有文件与 `manifest.json` 写完后原子切换为 current。只有新证据完整提交后才删除旧证据；启动、读取和写入时清理超过七天的孤立或过期目录。

清单使用相对文件名，不记录用户目录。完整窗口使用高质量 JPEG 控制体积，实际识别裁剪使用无损 PNG 保留网格像素；清单记录编码参数、原始尺寸、字节数、摘要和完整性。该设计复用现有文件系统能力，不新增图像或压缩依赖。

### 4. 证据作为多个系统诊断附件上传

反馈服务把结构化诊断 JSON、证据清单和图像作为系统生成附件统一校验与上传。系统附件不占五个手动附件名额，但所有文件继续遵守单文件 10MB 和总计 30MB 限制。组装前按以下顺序保留证据：所有识别裁剪图、最终一次完整游戏窗口、其余完整窗口、结构化诊断；发生取舍时清单列出省略项和原因。

选择多个附件而不是将图片 Base64 写入 JSON，是为了避免约 33% 的编码膨胀并让后台可以直接查看。选择不引入 ZIP，是为了避免新增压缩依赖和后台下载后解包步骤。上传仍使用现有私有 Storage 路径与反馈记录附件数组，不需要数据库迁移。

### 5. 以现有“附带诊断”选择作为上传授权

失败证据可以在识别失败时自动本地暂存，但不会后台上传。反馈页检测到证据后显示发生时间、尝试数、预计大小及“完整游戏窗口、仓库与裁剪图”说明；用户勾选附带诊断或提交对应诊断会话后才读取并上传。提交失败保留证据，云端反馈记录成功后才清理。

这一决定保留现有反馈交互和未授权不上传契约，同时满足用户希望优先获得完整排障材料的目标。无需增加第二个独立勾选项，避免用户误以为普通诊断已经包含图像。

### 6. 网格检测输出调试指标而不改变判定

识别器在现有算法计算过程中旁路收集候选横纵线数量、位置摘要、推算间距、等分边界偏差、网格置信度、占用数和阶段码。指标只写入证据清单，不参与阈值、成功判定或错误码选择。

这确保实施诊断增强不会意外“修复”或掩盖原问题，也方便用同一失败画面离线重放算法。

## Risks / Trade-offs

- [图像使反馈附件接近 30MB 上限] → 完整窗口使用高质量 JPEG、裁剪使用 PNG，并按规范优先级确定性省略低优先证据；清单始终说明完整性。
- [证据采集增加截图分析耗时] → 复用同一窗口截图，在分析结束后编码；采集失败旁路处理且不增加键鼠输入或识别重试。
- [应用异常退出留下临时文件] → 使用随机暂存目录、原子 current 指针和七天启动清理，不依赖正常退出。
- [多个系统附件触发现有数量假设] → 将手动附件与系统附件分别计数，并在客户端、主进程和云端契约测试中统一验证总容量及允许类型。
- [游戏窗口意外处于非目标页面] → 只允许已经通过前台游戏句柄校验的窗口，不截桌面；反馈页明确披露完整游戏窗口内容，由用户选择是否附带。
- [诊断实现影响当前未证实的识别修复] → 证据采集保持旁路，测试固定原结果、错误码、截图次数和输入次数。

## Migration Plan

1. 先增加证据清单、临时仓库和清理测试，再接入识别器图像与指标输出。
2. 接入反馈诊断附件组装和页面说明，保持旧诊断 JSON 在没有失败证据时完全兼容。
3. 运行海图识别、诊断、反馈校验、CloudBase 集成契约和全量测试，再运行开发版构建。
4. 仅在开发版使用可控失败画面验证完整窗口、裁剪标记和后台附件可查看性；本变更不执行打包或发布。
5. 回滚时停止生成新证据并移除反馈组装入口；旧临时证据由启动清理或七天过期规则删除，云端无需回滚数据结构。
