## Context

配置问题生成器目前为账号未认证和赛季为空分别产生 `account.poe-cn` 与 `account.league`，但两个问题在界面中都渲染 `AccountLeagueConfigurationField`。引导 Store 以问题 ID 维护历史、完成状态和剩余计数，运行失败映射也会使用这两个 ID 聚焦纠正项。参见 proposal.md 与本变更的 delta spec。

## Goals / Non-Goals

**Goals:**

- 在问题模型源头把账号和赛季归并为一个稳定问题，而不是仅在视图层隐藏第二项。
- 让初始预检、重检、运行失败聚焦和历史计数都使用相同的规范化问题 ID。
- 保留现有账号与赛季编辑器、Store、持久化字段和安全校验语义。

**Non-Goals:**

- 不合并账号与赛季的底层数据字段、IPC、网络请求或持久化逻辑。
- 不改变设置页“国服账号”区域，也不放宽账号或赛季缺失时的运行门禁。
- 不迁移现有用户数据，不处理打包或发布。

## Decisions

### 1. 在问题生成层创建组合问题

`accountIssues` 根据 `authenticated` 与 `league` 共同决定是否产生一个问题；任一条件不满足时使用组合名称，并根据缺失组合生成准确原因。这样列表、计数和重检天然只处理一项。

备选方案是在 `ConfigurationGuideDialog` 中把两个问题视觉合并。该方案会让 Store 仍计为两项，完成进度和失败聚焦继续重复，因此不采用。

### 2. 复用 `account.poe-cn` 作为规范问题 ID

组合问题沿用已经稳定存在且被多个入口识别的 `account.poe-cn` ID，并将旧的 `account.league` 输入在运行失败映射边界规范化到该 ID。编辑器只需处理规范 ID，同时兼容旧失败载荷，不产生第二个历史项。

备选方案是引入新的 `account.context` ID。它会扩大兼容映射和升级风险，却不增加用户可见能力，因此不采用。

### 3. 完成状态继续由完整重检决定

登录或赛季选择完成后仍触发现有完整配置重检；只有账号已认证且赛季有效时，组合问题才消失。不得通过编辑器局部事件直接把组合项标记完成，以免其中一个条件仍无效时提前放行。

### 4. 保持底层配置与安全边界不变

`AccountLeagueConfigurationField`、账号 Store、赛季持久化和认证 IPC 继续分别处理各自数据。变更只调整配置问题聚合与失败 ID 归一化，不接触凭据内容，也不改变继续按钮的最终校验。

## Risks / Trade-offs

- [旧代码或失败载荷仍传入 `account.league`] → 在失败映射入口统一规范化，并用回归测试覆盖赛季失败聚焦组合项。
- [只完成登录或只选择赛季时组合项被误判完成] → 组合问题生成条件同时检查两个状态，完成后仍执行全量重检。
- [问题历史中出现旧 ID 与规范 ID 两项] → 在进入引导历史前完成 ID 归一化，并测试初始缺失、运行失败和重检后的列表唯一性。

## Migration Plan

无需数据迁移。部署后新的引导会按当前账号摘要与全局赛季即时生成组合问题；回滚仅恢复旧的问题生成与映射逻辑，不影响已保存数据。
