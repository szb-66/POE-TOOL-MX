## Context

参见 `proposal.md`。每日使用服务已经确保正式版每个安装每个北京时间日期最多成功上报一次，但数据库入口仍需处理响应丢失后的重试与并发请求。当前数据库只保留每个安装的最新行并动态计算今天，无法支持历史趋势；迁移还由桌面端和私有反馈后台两个仓库共同保存。

## Goals / Non-Goals

**Goals:**

- 在不改变客户端行为的情况下，让数据库可靠维护匿名的每日正式版总数。
- 保留每安装一条最新记录的最小化模型，不新增可关联安装身份的日期历史。
- 维持匿名只写、服务角色只读和上报故障不影响应用的边界。

**Non-Goals:**

- 不修改 Electron 每日使用模块、重试节奏、载荷或本地成功标记。
- 不恢复心跳、并发在线统计、版本趋势或迁移日前回填。
- 不在本次应用生产迁移、部署或打包。

## Decisions

### 1. 每日总数与安装最新状态分离

新增 `app_daily_usage_totals`，以北京时间日期为主键，仅保存正式版去重总数和更新时间。`app_daily_usage` 继续以 `installation_uid` 唯一并保存最新运行元数据，因此不会新增“安装 × 日期”明细。

上报函数在单一事务中先尝试插入安装最新行；若 UID 已存在，则用“最后使用时间不属于当前北京时间日期”的条件更新判定跨日。同一 UID 的唯一约束和行锁让并发请求串行，只有首次插入或跨日条件更新成功时才原子递增当天总数。同日重复请求仍可刷新最新元数据，但不递增。

相比每日安装明细后查询 `count(distinct)`，预聚合设计不增加安装行为轨迹，读取最多 90 天时也只扫描每日行。相比定时快照，它不依赖额外调度器，也不会漏掉当天启动后很快离线的安装。

### 2. 迁移当天是可信历史起点

迁移创建汇总表后，以服务端北京时间当天范围查询现有最新行，并始终插入一条当天种子行，包括零人数。这样迁移日人数准确且最早行可作为采集开始日；旧记录只能证明各安装最后一次使用，不能用于推算更早每日总数，因此不回填迁移前日期。

`app_daily_usage_summary` 改为从汇总表提供历史日期、`packaged` 模式、计数和更新时间，保持现有对象名以兼容后台今日接口。基础表和视图撤销 PUBLIC、anon、authenticated 权限，仅向 service_role 授予读取；SECURITY DEFINER 上报函数是匿名写入汇总的唯一通道。

### 3. 两仓库共享一份迁移契约

迁移采用同一时间戳文件名并保持字节一致。桌面端测试负责验证匿名写入、同日幂等、跨日与权限边界；反馈后台测试额外验证迁移副本哈希以及历史提供器消费契约。客户端公开只写视图的列和请求体保持不变。

## Risks / Trade-offs

- [数据库函数并发竞态] → 使用唯一冲突、条件更新和行级锁串行化，并以真实 PostgreSQL 并发测试验证。
- [迁移日以前没有趋势] → 明确记录采集起点，不生成不完整回填。
- [同一天汇总递增后无法按安装删除] → 当前产品没有删除单个匿名使用记录的契约；汇总只作为匿名总量长期保存。
- [共享迁移副本漂移] → 测试比较两个文件的 SHA-256，提交时精确核对。
- [桌面工作区存在无关改动] → 不触碰现有修改，新增文件和定向测试独立核对。

## Migration Plan

1. 在两个仓库增加同名、字节一致的迁移和相应规范/测试。
2. 仅执行静态与开发测试，不调用生产 CloudBase、不打包桌面应用。
3. 后续获准发布时，由反馈后台流水线在依赖历史视图的函数部署前应用迁移。

如需回滚，先停止历史接口消费者，再恢复旧上报函数和只计算今天的汇总视图；聚合表默认保留以避免破坏性数据删除，另行确认后才移除。
