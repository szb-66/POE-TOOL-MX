## Context

首页当前同时负责业务状态派生和诊断会话 UI，诊断导出由渲染进程附加白名单模块与健康状态后调用主进程生成 schema v3 快照。问题反馈页已经能够选择普通诊断快照，但不知道诊断会话标识；反馈服务只接收布尔开关并调用无参数快照构建器。诊断事件存储已经持久化活动与最近会话，因此无需新增数据库或磁盘格式。

当前工作区包含尚未提交的反馈字段校验和紧急停止相关修改；实现必须只叠加本变更，不能回退这些修改。

## Goals / Non-Goals

**Goals:**

- 让问题反馈页成为诊断导出、诊断会话和反馈提交的唯一用户入口。
- 保留 schema v3、渲染器白名单状态、会话恢复、脱敏和反馈失败重试语义。
- 让本地导出与云端反馈生命周期解耦：导出不上传也不清除会话，成功反馈才清理会话。

**Non-Goals:**

- 不修改 CloudBase 表、存储策略、反馈历史或管理端能力。
- 不改变诊断事件格式、15 分钟时限、脱敏字段或会话结论算法。
- 不执行安装包构建或发布验证。

## Decisions

### 1. 将诊断生命周期抽成共享前端控制器

诊断会话状态、到期刷新、开始、结束、取消和本地导出从首页组合逻辑迁入独立组合函数。问题反馈组件独占诊断 UI；首页只继续计算看板状态，并把白名单 `modules` 与 `rendererHealth` 更新到轻量的共享诊断上下文。控制器生成导出/反馈载荷时读取该上下文，使入口迁移不丢失现有诊断字段。

备选方案是让反馈页直接实例化整个首页组合逻辑，但这会在设置页触发不必要的业务刷新和 store 副作用，因此不采用。

### 2. 诊断会话是显式诊断授权

普通“附带脱敏诊断”仍默认关闭。用户完成模块与现象选择并开始会话后，页面自动开启并锁定诊断开关；取消会话后恢复为可编辑的普通开关。页面挂载时若恢复到任意未清理会话，也按相同规则处理。

活动会话提交前由前端控制器先结束。若结束失败，反馈请求不发出；若后续反馈失败，会话保持为完成状态供重试。该顺序使用户可见状态与主进程持久状态一致。

### 3. 反馈 IPC 接收受控的可选会话标识

反馈提交载荷新增 `diagnosticCaptureId?: string`。校验层要求它只能与 `includeDiagnostics=true` 同时出现且符合 UUID 格式；反馈 IPC 在生成附件前通过诊断事件存储确认该会话存在，再以 `{ captureId }` 调用现有快照构建器。不存在或非法会话返回稳定、安全的反馈错误，不退化为普通快照。

反馈服务仅把会话标识传给诊断构建回调，不将其写入反馈正文或云端记录。反馈保存成功后 IPC 清理对应会话；任一失败阶段均不清理。

备选方案是把会话对象传入反馈服务，但会扩大信任边界并允许渲染进程提供伪造上下文，因此只传不可预测且需主进程解析的标识。

### 4. 本地导出不拥有会话清理权

“导出当前诊断”始终导出普通当前快照且不影响活动会话。活动会话的“结束并导出”先持久化完成状态，再导出对应会话；保存取消或成功后都保留会话。已完成、超时或中断会话可重复导出，直到用户主动取消或反馈成功。

## Risks / Trade-offs

- [共享的渲染器诊断上下文可能来自最近一次首页状态刷新] → 使用严格白名单和响应式更新；主进程环境、DPI、运行时与事件仍在生成时实时采集，缺少上下文时安全退化为空列表。
- [反馈保存成功但会话清理失败可能让旧会话再次出现] → 将反馈成功作为不可回滚结果，返回成功编号，同时安全记录清理原因并在页面刷新状态；不得重复上传或隐藏已成功提交结果。
- [设置分类通过 `v-show` 持续挂载会让到期定时器长期存在] → 控制器只为活动会话安排单个到期刷新，并在组件卸载时清理。
- [现有未提交代码与反馈组件重叠] → 使用最小补丁保留当前必填/最大长度校验及其他用户修改，完成后审查 diff 排除失败方案遗留。

## Migration Plan

1. 先增加会话标识校验、反馈快照构建与成功清理能力，保持旧布尔诊断提交兼容。
2. 增加共享诊断上下文和控制器，将问题反馈页接入并覆盖所有会话状态。
3. 移除首页诊断 UI 与旧控制逻辑，更新帮助和主规格。
4. 运行定向测试、完整测试、Vite 转换及 Electron 开发版交互验证；若需回滚，可恢复首页入口并继续使用向后兼容的普通诊断布尔提交。
