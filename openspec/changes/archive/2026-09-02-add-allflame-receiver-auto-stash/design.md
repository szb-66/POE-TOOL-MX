## Context

现有背包入库由一个 Pinia 设置、一个 Electron 背包检测消费者、公共 Python 界面检测进程和一个不可抢焦点的浮层组成。执行脚本启动后不再依赖界面标题，只在启动门禁阶段使用检测状态，因此接收舱只需要扩展配置与检测聚合，不需要复制扫描流程。公共检测器同时被混沌配方、仓库取件和君锋镇使用，必须保持既有状态字段语义兼容。

工作区已有与新手帮助相关的未提交修改，并与入库页面存在轻微重叠；实现必须进行局部补丁并保留现有导入和帮助数据改动。

## Goals / Non-Goals

**Goals:**

- 让普通仓库与永火接收舱拥有独立持久化开关和独立模板门禁。
- 让任一已启用目标就绪时驱动同一个浮层和同一套安全入库执行。
- 保持其他公共检测消费者和旧配置兼容。

**Non-Goals:**

- 不创建第二个浮层、第二个扫描脚本或目标专属黑名单/布局。
- 不改变入库点击、传奇强入、前台门禁、停止与统计语义。
- 不打包、发布或自动归档变更。

## Decisions

### 使用单个检测消费者聚合两个独立开关

背包运行配置携带 `moduleEnabled` 与 `allflameReceiverEnabled`。前端启停操作统一走“协调检测”流程：任一开关开启时注册或更新同一个 `bag` 消费者，两个开关均关闭时才注销。相比创建第二个消费者，这能避免同一业务重复订阅、重复浮层和互相重启检测器。

### 对检测事件做加法扩展

Python 匹配器新增接收舱模板与 `allflameReceiverReady`，公共协调器原样转发；既有 `ready`/`stashReady` 继续只代表普通仓库与背包就绪。背包 IPC 使用 `(moduleEnabled && stashReady) || (allflameReceiverEnabled && allflameReceiverReady)` 计算有效就绪。相比复用 `ready` 表示任意目标，这能避免改变混沌配方等消费者行为。

### 保持执行 IPC 无目标参数

两个目标最终都对背包格执行相同 Ctrl+点击流程，且启动后标题失配不应终止扫描。因此 `start-bag-stash` 不新增目标参数，点击浮层时只依赖已经聚合的有效就绪门禁。这样不会产生两套配置快照或目标分支。

### 共享模板设置增加接收舱字段，功能卡提供直接采集入口

接收舱模板沿用现有 `TemplateCaptureConfigurationField`、原子 PNG 保存、开发版 `.dev.png` 命名、DPI/显示器元数据校验和配置纠错。模板数据保存在共享界面检测设置中，启用状态保存在背包设置中。接收舱功能卡直接展示采集入口，减少用户跨页面配置。

### 入库运行状态只展示一次

入库 Tab 顶部使用两张并列功能卡展示独立开关和检测状态；共享的进度、统计、停止按钮和扫描规则位于功能卡之外。相比在两张卡中复制运行状态，这能避免同一轮扫描出现两份统计或让用户误以为存在两个并行任务。

## Risks / Trade-offs

- [接收舱模板增加检测开销] → 仅在配置了模板时加载和匹配，并继续在游戏后台完全跳过截图。
- [关闭一个功能时误停另一个] → 将检测生命周期绑定到两个开关的 OR 聚合，只有全部关闭才注销消费者。
- [新增状态污染其他业务] → 保持所有旧字段语义不变，仅添加接收舱字段并由背包 IPC 私有聚合。
- [模板或 DPI 配置失效导致误输入] → 启用前复用现有模板环境校验，失败关闭且不启动检测或键鼠输入。
- [当前工作区修改冲突] → 只通过小范围补丁修改入库页面，验证 diff 不回退已有帮助改动。

## Migration Plan

1. 设置归一化为旧数据补充关闭的接收舱开关和空模板字段。
2. 检测协议以新增字段方式部署，旧消费者无需迁移。
3. 若需要回滚，忽略新增设置字段并恢复旧检测聚合即可；普通仓库模板和执行接口未改变。
