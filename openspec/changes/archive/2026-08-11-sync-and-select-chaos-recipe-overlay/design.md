## Context

商城配方快照由主进程服务持有，当前配方和单件配方勾选由主窗口 Pinia store 持有，控制浮窗则从主进程中的运行时副本派生状态。刷新时服务会先提交并发布新快照，渲染层随后重置单件选择并按启用状态再次同步运行时；刷新、选择和浮窗发布分散在不同边界，缺少一个能够断言“本次刷新完整状态已经提交”的回归入口。浮窗目前只显示当前配方，没有修改 `activeRecipeId` 的 IPC。

## Goals / Non-Goals

**Goals:**

- 将一次刷新得到的快照及其派生选择作为同一修订提交给控制浮窗。
- 让浮窗和主界面复用现有配方目录、当前配方与单件选择语义。
- 配方变更在空闲状态立即生效，并继续受现有校准、前台和互斥锁门禁保护。

**Non-Goals:**

- 不改变仓库 API、配方计算算法、坐标校准或 Python 取件脚本。
- 不允许在运行、暂停或预览期间热切换现有计划。
- 不新增独立配置文件或第二套配方持久化。

## Decisions

### 1. 以完整控制运行时提交作为刷新完成边界

商城配方 store 在收到刷新快照后，先归一化仓库页和全部单件配方选择，再以一个完整运行时载荷提交 `activeRecipeId`、目标套数和按配方分组的单件选择。主进程控制器仅在完整载荷落地后发布最终浮窗状态；服务仍可在物品实际消费、注销等不经过渲染层的路径触发状态重算。

这比在首页按钮旁追加一次专用“通知浮窗”调用更可靠，因为后者仍会遗漏商城详情页、自动刷新等同级调用方；也不需要为快照另建事件总线。

### 2. 复用配方目录生成浮窗选项

控制器使用既有配方 ID、标签、类型和当前快照生成选项，套装配方显示完整套数，单件配方显示该配方已选择的候选件数。运行时保存按配方分组的单件选择，使用户从浮窗切到任一单件配方时不会错误复用上一个配方的物品 ID。

不在 Vue 浮窗中复制配方目录或计算数量，避免主窗口和浮窗出现两套口径。

### 3. 浮窗切换先更新主进程，再通知主窗口持久化

新增窄范围 IPC 接受受支持的配方 ID。主进程验证空闲状态和配方 ID后立即更新控制运行时并返回新状态，同时向主窗口广播选择结果；Pinia store 接收后更新现有 `settings.activeRecipeId`、调整目标套数并写入原有 localStorage，随后通过既有运行时同步自然收敛。

与只通知主窗口再等待其回传相比，该方案不会让浮窗交互依赖渲染调度；与把全部商城设置迁到主进程相比，改动更小且没有配置迁移。

### 4. 使用无焦点指针菜单切换配方

控制浮窗必须保持 `focusable: false`，避免从游戏抢走键盘焦点；原生 `<select>` 依赖焦点和系统下拉菜单，在该窗口模式下无法可靠展开。配方选择因此使用与现有操作按钮一致的 `pointerdown` 菜单：先展开全部配方，再点击目标配方。控制状态继续输出 `canSelectRecipe` 和禁用原因；运行、暂停、预览或任一浮窗操作处理中，菜单按钮原生禁用。按钮空闲文案固定为“取出配方”，现有停止/继续文案不变。

## Risks / Trade-offs

- [主进程即时选择与主窗口持久化之间存在短暂窗口] → IPC 返回前已更新浮窗，主窗口事件随后用现有串行运行时提交收敛；测试覆盖事件往返和最终一致性。
- [旧运行时只有当前配方的一维 `selectedItemIds`] → 归一化时兼容旧字段，并仅新增内存载荷字段，不迁移用户存储结构。
- [刷新发布两次造成短暂中间态] → 回归测试断言刷新 Promise 完成时的最后一次浮窗状态；发布器继续合并加载期高频状态。
- [配方选择增加浮窗宽度] → 复用现有内容尺寸观测与窗口自适应，不写死新宽度。

## Migration Plan

无需数据迁移。开发版先运行目标 Node 测试和 Vite 组件转换，再运行完整 `npm test` 与 OpenSpec 严格校验；若回滚，移除新增选择 IPC、浮窗选择控件和分组选择运行时字段，原有 `activeRecipeId` 与刷新路径仍可工作。
