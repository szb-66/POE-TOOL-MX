## Context

当前主窗口的 `did-fail-load` 监听为空，主进程顶层 ready Promise 没有统一失败处理，也没有监听 preload、渲染器及 GPU 子进程退出。已有诊断事件库依赖页面成功启动后由用户导出，无法覆盖白屏闪退。工作区存在两个未接入的同步日志和崩溃保护草稿，需要保留思路但修正异常吞噬与错误的 GPU 原因分类。

## Goals / Non-Goals

**Goals:**

- 在创建任何 BrowserWindow 前建立同步文本日志与本地 Crashpad 监控。
- 通过稳定原因码串联主进程、页面、preload、渲染端和 Chromium 子进程的启动状态。
- 对有限且明确的早期崩溃进行至多一次安全模式重启。
- 建立开发环境可自动验证的故障反馈环。

**Non-Goals:**

- 不推断或宣称已修复当前无法复现的用户侧根因。
- 不上传、解析或符号化 minidump，不引入远程崩溃服务。
- 不构建或发布新的安装包。

## Decisions

### 使用同步启动日志和独立结构化记录函数

最早阶段使用同步追加，确保原生或进程级退出前尽可能落盘。记录函数接受 `phase/outcome/reasonCode/message/timestamp`，统一做长度限制和脱敏。相比复用异步诊断事件库，它不依赖 ready、IPC 或事件循环继续存活。

### Crashpad 只保存在用户数据目录

在 ready 前设置 `crashDumps` 路径并调用 `crashReporter.start({ uploadToServer: false })`，覆盖随后创建的主进程和子进程。文本日志提供可读上下文，minidump保留原生崩溃证据，两者均不自动上传。

### 将诊断收集和恢复策略分离

Crash guard 负责安装监听及记录；纯函数负责根据进程类型、退出原因、启动时长和安全模式状态判断是否恢复。只有 GPU 类型子进程崩溃或渲染器 `crashed/abnormal-exit` 可恢复，其他原因只报告。

### 使用启动参数阻止恢复循环

恢复时保留原参数并去重加入 `--disable-gpu` 与 `--startup-safe-mode`，随后调用 `app.relaunch` 和 `app.exit`。再次启动检测到安全模式参数后永不自动重启。相比持久化恢复标记，参数不会污染后续正常启动。

### 使用 preload 暴露最小启动上报接口

preload 只暴露固定的 `reportStartupEvent` 方法；主进程 IPC handler 验证事件枚举、结果枚举、原因码格式和消息长度。Vue 在挂载后报告成功，并在全局 error/unhandledrejection 中报告启动失败。

### 开发故障注入由显式参数控制

测试入口必须同时满足 `NODE_ENV=development` 和已知参数，避免正式包意外触发。真实渲染器崩溃使用 Electron 自带能力，其他阶段使用定向抛错或无效加载目标。

## Risks / Trade-offs

- [主进程原生崩溃可能来不及写最后一行文本] → Crashpad 提供补充证据，并在每个阶段开始前同步记录。
- [禁用 GPU 可能降低界面性能] → 只在一次恢复进程中生效，不保存为永久设置。
- [异常堆栈可能暴露路径或认证数据] → 写入前统一脱敏并限制单字段长度，不记录任意对象。
- [错误恢复策略掩盖非 GPU 问题] → 恢复判断采用白名单，页面加载、OOM、完整性失败和被外部终止均不恢复。
- [本地转储包含进程内存片段] → 不自动上传，错误提示说明仅在用户主动提供时分享。

## Migration Plan

无需数据迁移。开发版验证通过后另行打包；回滚时移除启动监听和 IPC 接入即可，既有用户配置不受影响。日志与转储目录可留存供用户自行删除。
