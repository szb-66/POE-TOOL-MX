## Context

参见 `proposal.md`。当前已有 `GameWindowTitleRegistry` 维护标题和进程名配置，也已有助手主窗口原生恢复实现，但游戏激活代码仍分布在查价模块和多个 Python 脚本中；部分业务管理器直接调用主窗口 `focus()`。这使窗口选择、失败码和前台确认无法保持一致。

## Goals / Non-Goals

**Goals:**

- 让主进程成为游戏窗口激活与助手主窗口恢复的唯一编排入口。
- 让所有从助手发起的截图或输入流程在创建业务进程前完成可信游戏激活。
- 保留脚本逐输入前台校验、自动化互斥、紧急停止和现有焦点归还时机。
- 用架构测试阻止业务代码重新引入窗口枚举、Win32 前置或主窗口直接聚焦。

**Non-Goals:**

- 不统一登录窗、查价浮窗、识别反馈层等辅助窗口的显示或焦点策略。
- 不把任意窗口激活能力暴露给 renderer。
- 不在本变更中重写持续前台监视器，也不改变各业务何时恢复助手或归还游戏焦点的产品策略。
- 不执行安装包构建、规范同步或变更归档。

## Decisions

### 1. 主进程持有单例窗口激活服务

创建主进程单例服务并通过依赖注入交给窗口管理器、自动化管理器和 IPC 组合层。内部接口为：

- `activateGame({ source }) -> Promise<{ success, code, target? }>`
- `activateMain({ source }) -> Promise<{ success, code }>`

`source` 只用于有限诊断标识；`target` 只允许返回截断后的标题与进程文件名，不包含句柄或完整路径。稳定码至少区分成功、平台跳过、目标缺失、权限不匹配、系统拒绝、目标变化和主窗口不可用。

选择该方案而不是业务模块导入底层函数，是为了让激活目标、错误映射和前台复核只有一个所有者，并避免 renderer 或业务配置扩大系统输入边界。

### 2. 复用现有配置注册表并集中 Windows 原生实现

游戏激活读取 `GameWindowTitleRegistry` 的当前内存快照，使用共享候选选择规则：标题优先级、非最小化、当前前台、可见面积。Windows 原生辅助代码只存在于窗口激活模块中，负责枚举有限窗口元数据、恢复最小化目标、附加输入线程、调用前台切换并复核最终句柄与标题/进程身份。

助手恢复继续复用现有原生句柄与 Electron 回退算法，但只能由单例服务调用。查价模块中的游戏聚焦脚本迁入该模块，原模块仅保留剪贴板前台门禁和复制职责。

选择集中内嵌的固定原生辅助代码而不是新增可替换脚本文件，可避免新增安装资源和动态脚本路径，同时保持调用参数仅由主进程生成。

### 3. 激活发生在业务进程创建之前

从助手发起且可能截图或输入的入口先获取现有自动化锁或保留其原有互斥顺序，再调用 `activateGame`，成功后才写运行配置和创建 Python 进程。调用点按现有同步/异步契约调整为可等待的启动方法；失败路径负责释放已取得的锁并返回业务可显示的中文错误。

屏幕选取仍由窗口管理器先最小化主窗口，再调用统一游戏激活；结束后在 `finally` 中调用 `activateMain`。全局快捷键从游戏内触发的流程仍调用同一服务；若游戏已经是可信前台，服务直接返回成功而不重复切换。

### 4. Python 只保留安全门禁

删除固定脚本和生成模板中的 `find_game_window`、`focus_game_window`、`activate_game_window` 以及 `activateGameWindow` 等启动标志。被其他脚本导入的聚焦符号同步移除。每个脚本继续读取同一配置文件并保留 `window_matches_game`、`is_game_foreground`、`require_game_foreground`，用于每次原子输入前失败关闭。

这比保留脚本回退激活更安全：主进程无法激活时不会由脚本采用另一套规则继续抢焦点，也不会发生首次失败后在运行中重新激活。

### 5. 迁移只统一机制，不改变焦点策略

浮士德、海图、背包扫描和选取流程在原本要求恢复助手的位置改用 `activateMain`；查价浮窗只在现有允许原因下调用 `activateGame`；其他业务不因本重构新增结束后恢复。第二实例和主窗口 IPC 也使用 `activateMain`，但辅助窗口继续使用自身 `focus()`。

## Risks / Trade-offs

- [大量同步启动方法需要异步化，可能改变 IPC 返回时序] → 保持响应结构不变，为每个入口增加“激活失败不创建子进程”的回归测试。
- [锁已取得但激活失败可能遗留占用] → 每个迁移入口使用单一 `try/finally` 或统一启动事务释放锁并清理临时配置。
- [现有脚本导入其他脚本的聚焦函数] → 先建立调用清单，再同时修改导出与导入，最后用架构搜索测试确保没有残留符号。
- [Windows 权限或前台限制导致误报成功] → 成功必须以最终前台句柄和可信身份复核为准，Electron `focus()` 调用本身不视为成功。
- [当前工作区已有浮士德局部修补] → 保留标题加进程门禁测试，将其窗口激活实现删除或迁移，完成后检查并清理所有临时或重复代码。

## Migration Plan

1. 先建立窗口激活服务及候选、错误码、助手恢复测试，保持旧调用点不变。
2. 将查价和屏幕选取切到服务，验证两个方向的激活基础路径。
3. 按制作/地图、背包/配方/君锋镇、海图、浮士德顺序迁移启动入口；每组完成后运行对应测试。
4. 删除 Python 自带激活实现与启动标志，更新导入和生成模板。
5. 增加架构约束测试并清理旧原生聚焦代码、局部补丁遗留与未使用依赖。
6. 在开发版完成含游戏名浏览器页签与真实游戏并存的人工验证；失败时可按调用组回退到迁移前入口，公共服务本身不改变持久数据。
