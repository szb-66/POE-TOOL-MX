## Context

参见 [proposal.md](./proposal.md) 的动机。当前黑名单规则以 `{ field, keyword, matchMode }` 对象保存在浏览器 `localStorage` 的 `bagSettings.blacklist` 中，由前端统一规范化后随检测启动配置穿过 Electron IPC，最终由 Python 脚本再次规范化并匹配。页面在模块运行期间已锁定黑名单的新增和删除，运行进程使用启动时的配置快照。

这项变更横跨页面、前端配置模型、持久化、跨进程配置和 Python 匹配器；前后两端必须对旧规则及停用语义保持一致。

## Goals / Non-Goals

**Goals:**

- 用同一个规则对象表达并持久化单项生效状态。
- 确保停用规则保留原内容但在 JavaScript 和 Python 匹配入口都不会命中。
- 让缺少生效字段的旧规则无损迁移并继续保持启用。
- 保持检测进程配置快照和“运行期间不可编辑”的现有一致性模型。

**Non-Goals:**

- 不允许在正在运行的检测或入库轮次中热更新黑名单。
- 不增加规则排序、批量启停、编辑字段/关键词或规则分组。
- 不改变黑名单命中统计和多格物品占位跳过语义。

## Decisions

### 1. 在规则对象上增加 `enabled` 布尔字段

规则规范化后的形态统一为 `{ field, keyword, matchMode, enabled }`。`enabled: false` 是唯一的停用表达；缺少字段或其他值均规范化为 `true`，使所有旧规则升级后继续生效。

这比维护独立的停用索引数组可靠：规则可增删且没有稳定 ID，索引会漂移；按字段和关键词定位又无法可靠区分重复规则。为本需求引入规则 ID 会扩大迁移和交互复杂度，因此不采用。

### 2. 完整规则随运行配置传递，在匹配器中忽略停用项

前端 `normalizeBagBlacklist` 保留 `enabled`，`buildBagRuntimeConfig` 和 Electron `runtimeConfig` 按现有黑名单数组传递全部规则。JavaScript `findBagBlacklistMatch` 与 Python `normalize_blacklist`/`find_blacklist_match` 使用相同默认启用规则，并在匹配时跳过 `enabled: false` 的项。

不在 IPC 边界预先删除停用规则，因为完整快照更易诊断并保持规则模型一致；匹配器才是“是否参与匹配”的权威边界。两种语言各自规范化则延续现有防御性输入处理，避免外部或旧调用绕开前端规范化。

### 3. 列表内使用开关并通过现有 `setBlacklist` 持久化

黑名单表增加“生效”列，每行使用开关展示 `enabled`。切换时创建只替换目标行的新数组并调用 store 的 `setBlacklist`，复用现有规范化和 `localStorage` 保存路径。新增规则显式写入 `enabled: true`，停用行继续展示其匹配字段、方式和关键词。

开关与新增、删除控件一样在 `moduleEnabled` 时禁用，并沿用现有“请先关闭模块”提示。这与启动时冻结运行配置的模型一致，避免界面显示已切换但当前进程仍使用旧快照的歧义。相比增加运行期 IPC 热更新，这一方案不需要解决正在执行轮次的原子更新边界。

### 4. 以行为测试覆盖两种语言和页面契约

扩展现有 `bagAutoStash.test.js`：验证 JavaScript 规范化的默认/显式状态、停用不匹配、重新启用后匹配、运行配置保留状态；通过现有 Python 子进程测试验证相同迁移及匹配语义；页面源码契约验证生效开关、禁用条件和切换处理器存在。现有黑名单精确/模糊、多格物品和整体测试继续作为回归门禁。

## Risks / Trade-offs

- [JavaScript 与 Python 对默认值解释不一致] → 两端都采用“仅严格的 `false` 表示停用”，并用同一组旧规则、启用规则和停用规则用例验证。
- [用户切换后误以为正在运行的模块立即更新] → 模块运行时禁用开关并保留关闭模块后修改的提示；重新启动检测时生成新快照。
- [停用行视觉上仍像有效规则] → 增加独立“生效”列，关闭状态由开关直接表达，同时保留规则文本以便辨认和恢复。
- [回退到不认识 `enabled` 的旧版本会丢失停用状态] → 新版本无需单独迁移即可前向兼容；若回退旧版本，旧规范化会把规则视为启用，这是旧程序能力限制，重新升级后需再次停用相关项。

## Migration Plan

1. 发布后首次加载 `bagSettings` 时，由前端规范化为每条有效旧规则补充 `enabled: true`，store 初始化保存会写回新形态。
2. 检测启动时把含 `enabled` 的完整规则数组传入 Electron 和 Python；Python 对直接传入的旧规则也默认启用。
3. 无需数据库迁移或配置版本提升；空黑名单和无效规则继续按现有逻辑处理。
4. 若必须回滚应用代码，配置仍是合法 JSON，但旧版本会忽略并可能在再次保存时移除 `enabled`，所有保留规则按启用处理。
