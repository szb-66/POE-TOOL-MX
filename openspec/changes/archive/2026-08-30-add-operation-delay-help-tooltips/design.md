## Context

参见 `proposal.md` 的动机。“操作延迟”区目前由三个模板形态组成：单独渲染的“自动操作等待”和自适应相关字段，以及从字段数组循环渲染的物理输入、固定结果等待。设置页已经在其他区域使用 `label-with-help`、`el-tooltip`、`QuestionFilled` 和可聚焦图标，因此无需引入新的交互模式。

## Goals / Non-Goals

**Goals:**

- 让 11 个可配置时序项都有与实际自动化语义一致的就地说明。
- 让循环渲染字段的名称、说明和键保持同一数据来源，减少漏配或错配。
- 保持鼠标与键盘均可访问问号提示，并可通过页面结构测试核对完整覆盖。

**Non-Goals:**

- 不调整任何时序值、默认值、字段名称、分组或条件显示规则。
- 不改变自适应检测算法、固定等待的使用位置或自动校准逻辑。
- 不新增帮助页主题、设置存储字段、IPC 或 Python 配置字段。

## Decisions

### 1. 在字段标签旁使用现有问号提示

所有项目通过表单标签插槽呈现“字段名 + 可聚焦 QuestionFilled 图标”，提示由现有 `el-tooltip` 承载，图标的 `aria-label` 包含具体字段名。这样与设置页的背包网格、连续空格判空和物品位置说明保持一致，也不会额外占用表单纵向空间。

替代方案是保留或扩展字段下方的 `hint-text`，但这无法满足每项都有问号入口，并会让 11 条详细说明显著拉长页面。

### 2. 用字段元数据集中维护说明

为时序字段建立以配置键为索引的说明映射；由 `PHYSICAL_TIMING_FIELDS` 和 `RESULT_TIMING_FIELDS` 生成的字段对象同时携带 `label` 与 `help`。单独渲染的 `operationDelayMs`、`adaptiveTiming`、`adaptiveTimeoutMs` 也从同一说明映射读取文案。

这能让测试按配置键核对 11 项完整覆盖，避免模板里散落多份长字符串。替代方案是在每个模板分支直接写死说明，但循环字段仍需额外分支，后续更容易出现字段存在而说明缺失。

### 3. 说明描述动作边界，不承诺模块全覆盖

文案说明数值发生在“按下后”“释放后”“切换仓库页签后”等动作边界，并明确自适应与固定模式的关系。除“自动操作等待”已由主规范声明支持范围外，说明不枚举可能变化的所有业务模块，以免新模块接入同一时序协议后文案立刻过期。

### 4. 使用结构测试约束完整性

在现有设置页测试中验证 11 个字段键均有非空说明、两组循环字段把说明绑定到问号提示、三个单独字段也显示问号，并检查 `tabindex="0"` 与字段特定 `aria-label`。验证同时保留原有自适应条件显示断言，不需要启动会产生游戏输入的自动化。

## Risks / Trade-offs

- [提示文案与底层时序语义日后漂移] → 说明映射使用配置键组织，并通过测试要求所有已知字段有说明；改变时序协议时可在同一位置同步更新。
- [较长说明在窄窗口中阅读困难] → 复用 Element Plus tooltip 的换行能力，并通过合适的最大宽度或内容容器保证可读性，不把说明压缩成模糊短句。
- [只验证源码结构可能遗漏视觉对齐问题] → 实施阶段除节点测试和 Vite 转换外，在开发版设置页实际检查问号位置、悬停、键盘聚焦和条件分支。

## Migration Plan

该变更只增加渲染元数据和提示入口，无数据迁移。回滚时删除新增说明映射与标签提示即可，现有设置数据和运行时协议不受影响。
