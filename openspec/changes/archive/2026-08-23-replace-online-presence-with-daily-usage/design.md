## Context

参见 `proposal.md`。现有主进程在开发版和正式版均启动 60 秒心跳，通过匿名令牌向写入视图 POST，数据库以每安装一行和三分钟视图计算在线数。当前上报身份、只写视图和 RLS 边界可复用，但调度、本地去重与数据库命名需要整体替换。

## Goals / Non-Goals

**Goals:**
- 把每安装每日数据库请求限制为一次成功上报，并让开发版产生零请求。
- 以北京时间和服务端身份/时间形成可验证的每日去重统计。
- 保留已有匿名安装记录、安全边界和非关键失败语义。

**Non-Goals:**
- 不记录每日历史、昨日人数、趋势、账号数或功能使用明细。
- 不打包、发布、部署 migration 或修改远端 CloudBase。
- 不兼容仅由维护者测试的旧 1.1.0 高频心跳客户端。

## Decisions

1. **复用 PostgreSQL 与匿名身份，不新增 Presence 基础设施。** 每日一次后请求量理论上下降至原来的 1/1440；相比新增云函数或外部 KV，此方案保持现有安全边界和运维面。
2. **使用本地成功日期作为成本门禁，数据库行作为权威去重状态。** 主进程在认证前读取 `userData/feedback/daily-usage-date`；只在成功响应后以原子替换方式保存 `YYYY-MM-DD`。文件丢失或损坏最多造成额外 upsert，不会重复计数。
3. **北京时间调度、服务端时间入库。** 客户端仅计算是否需要请求和下一次 00:05；请求体不携带 UID、日期或时间，数据库函数从 `auth.uid()` 和 `statement_timestamp()` 获取权威值。
4. **失败重试有严格日上限。** 首次失败后依次等待 15 分钟、1 小时、6 小时；当天三个重试机会耗尽后停止。401 重新认证属于同一次上报尝试，不额外消耗日重试预算。
5. **版本化迁移重命名并替换对象。** 将表和时间列改为每日使用语义，创建新的只写入口、触发函数和汇总视图，删除旧在线视图/函数/策略；迁移保留表中现有行并附回滚说明。
6. **主进程生命周期保持非阻塞。** 服务只在 `app.isPackaged` 时启动；退出时清理跨日与重试计时器，网络错误继续在调度边界吞并。

## Risks / Trade-offs

- [本地时钟错误可能提前或延后请求] → 客户端日期只负责降低调用，数据库始终使用服务端时间决定统计日期。
- [应用在 00:05 休眠] → Windows 恢复后定时器执行并补报；新一天启动也会立即补报。
- [数据库单次唤醒仍产生少量 CU] → 发布后观察 24 小时小时级用量；若仍不可接受，再单独设计非 PG 状态后端。
- [旧客户端继续请求旧入口] → 旧版本仅为自有测试，切换前关闭所有实例，不保留兼容对象。

## Migration Plan

1. 在本地完成 additive-to-breaking migration、服务和测试，不连接生产环境。
2. 获得部署与打包确认后，先关闭所有旧测试实例，再应用 migration、部署后台读取端并发布新桌面端。
3. 读取 schema、GRANT/RLS 和汇总结果，确认新入口可写、匿名不可读。
4. 观察至少 24 小时 PostgreSQL CU 与 `app_daily_usage` 更新次数。
5. 回滚时恢复旧表/列名、在线视图与心跳入口，并回退桌面端；回滚会恢复高频消耗，仅用于功能性应急。
