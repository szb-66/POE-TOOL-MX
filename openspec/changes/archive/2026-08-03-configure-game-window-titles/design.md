## Context

窗口标题目前由主进程 DPI 探针和八个独立 Python 脚本分别硬编码。设置由渲染进程 `localStorage` 持久化，Python 子进程均由 Electron 主进程生成或启动，并继承主进程环境变量。部分进程长期运行且以较高频率检查前台窗口。

## Goals / Non-Goals

**Goals:**

- 让所有窗口识别入口使用同一份有序配置和相同的包含匹配语义。
- 在不重启长期 Python 进程的情况下传播更新，同时控制高频读取开销。
- 保持旧用户设置和共享配置读取失败时的安全默认行为。

**Non-Goals:**

- 不为每个名称增加独立匹配模式、正则表达式或进程名过滤。
- 不改变同一名称内已有的窗口可见性、最小化恢复或面积选择策略。
- 不执行打包、发布或安装包兼容验证。

## Decisions

### 使用共享规范化模块维护设置数据

渲染端提供默认列表、规范化与校验函数，设置 Store 只持久化有效数组。更新通过异步 IPC 先提交主进程，成功后再替换 Store 并写入 `localStorage`，失败则保留原值。相比允许任意数组进入 Store，这可保证 UI、运行时文件和持久化状态一致。

### 主进程维护固定路径的原子共享文件

主进程启动时在用户数据目录初始化 `game-window-titles.json`，并设置固定环境变量供之后启动的 Python 进程继承。IPC 更新将临时文件原子替换为完整 JSON；路径本身不变，因此已运行进程也能看到内容变化。相比重启每个子进程，该方案不会中断自动化；相比为每种 IPC 配置单独透传，可覆盖生成脚本和静态资源脚本的全部入口。

### Python 脚本按修改时间缓存共享列表

每个脚本保留默认列表和共享文件缓存，仅在文件修改时间变化时重新解析。前台检查接受任意名称；候选枚举为每个窗口计算最早命中索引，并按索引优先、再按模块既有规则选择。相比每轮无条件解析文件，这能避免自动喝药和公共界面检测的高频磁盘开销。

### 名称优先级高于候选状态

跨名称时先比较配置索引；只有命中同一最早名称时才比较前台、最小化或面积。这直接兑现用户排序语义，即低优先级窗口即使当前位于前台，也不会覆盖已存在的高优先级候选。

## Risks / Trade-offs

- [Python 代码需要在多个独立脚本中保持一致] → 通过统一占位片段生成可嵌入模板，并用测试扫描全部脚本的加载与优先级契约。
- [Windows 原子替换可能被短暂占用] → 主进程保留上一份内存配置并返回结构化失败，渲染端不提交本地状态；读取端继续使用缓存或默认值。
- [正在执行的一组输入中途发生配置变化] → 不重启或中断进程，新列表只在既有的下一次窗口安全校验点生效。
- [共享文件被用户手动损坏] → 读取端拒绝空列表与无效 JSON并回退默认列表，避免扩大可输入窗口范围。

## Migration Plan

1. 主进程以默认列表初始化共享文件和环境变量。
2. 渲染端加载旧设置；缺少或无效字段时规范化为默认列表并同步主进程。
3. 更新后的所有脚本优先读取共享文件，读取失败时使用内置默认值。
4. 回滚代码时旧版本忽略新增的 `localStorage` 字段；共享 JSON 文件不影响旧脚本。
