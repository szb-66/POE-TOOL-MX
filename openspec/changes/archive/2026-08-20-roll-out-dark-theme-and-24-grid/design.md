## Context

当前工作树已包含主框架、首页、设置页和公共 Element Plus 覆盖样式的深色试点，但主题以 `main-window-theme` 为唯一作用域，并主动排除全部 `noLayout` 路由。其余一级页面仍混用局部 CSS Grid、Flex 和硬编码卡片样式；7 个业务悬浮窗各自维护蓝色或高饱和硬编码色，同时依赖固定尺寸、透明窗口和坐标契约。

## Goals / Non-Goals

**Goals:**

- 在不覆盖现有试点改动的前提下建立可复用的主题作用域、24 栅格约定和紧凑悬浮窗变体。
- 让页面级布局可通过统一断点和 span 直接检查，减少每页重复响应式规则。
- 将视觉变化与 Electron 窗口行为隔离，使样式重构不改变自动化和覆盖层安全边界。

**Non-Goals:**

- 不重新设计业务流程、信息架构、路由、IPC、数据模型或持久化设置。
- 不迁移物品槽位、地图/谜题坐标、图表和其他业务专用网格。
- 不改造调试层、坐标选择器，不增加主题切换，也不执行安装包构建。

## Decisions

### 共享视觉令牌与窗口作用域分离

将现有主题拆为共享深色令牌、主窗口容器规则和业务悬浮窗紧凑规则。主布局路由同时挂载共享主题与主窗口作用域；白名单业务悬浮路由挂载共享主题与悬浮窗作用域；调试层和坐标选择器均不挂载。

选择路由白名单而不是让全部 `noLayout` 路由继承主题，因为 `noLayout` 同时包含业务悬浮、诊断和区域选择三种不同窗口语义，统一继承会破坏标定与调试可见性。

### 使用 Element Plus 原生 24 列能力

页面级布局统一使用 `el-row`、`el-col` 及共享 `app-grid` 样式；水平 gutter 固定为 16px，共享样式补足相同的纵向间距。标准 span 为单列 24、双列 12、三列 `xs=24/sm=12/md=8`、四列 `xs=24/sm=12/md=6`，主从布局为 `xs=24/sm=24/md=16+8`。

选择现有组件库能力而不是新增自研 Grid 组件，可避免重复实现断点、负边距和响应式属性，并使模板中的列意图可直接检查。业务专用内部布局保留 CSS Grid 或 Flex，避免为形式统一破坏其尺寸语义。

### 悬浮窗使用独立紧凑密度

业务悬浮窗通过变量固定 4/6/8px 间距、4/6px 圆角、11/12px 字号和 26/30px 控件高度；复用主窗口色彩与状态令牌，但不复用主窗口的 16px 栅格 gutter 和卡片内边距。样式调整必须适配现有窗口边界，固定尺寸窗口不扩大；剧情的自动高度和查价的用户缩放行为保持不变。

选择独立密度层而不是直接复用主窗口组件尺寸，是因为悬浮窗长期覆盖游戏画面且可用面积有限，信息密度与遮挡成本高于主窗口。

### 现有试点作为迁移基线

保留工作树中已有主题、布局、规范和测试差异，在实现阶段先为其补齐变更归属，再在该基础上推广到剩余页面。不得通过 reset、checkout 或覆盖写入回退现有试点；发现重复或失败方案时，只删除已确认被共享实现替代的代码。

## Risks / Trade-offs

- [大范围页面改造可能产生局部溢出或双滚动] → 逐页检查默认、窄屏和最大化尺寸，并保留每页唯一整页滚动区。
- [共享主题可能通过 `html` 或传送组件泄漏到排除窗口] → 以路由类别测试主题类挂载，并将页面背景与共享令牌放在不同作用域。
- [紧凑悬浮样式可能降低可操作性] → 固定控件高度下限、焦点轮廓和文本完整性，并在明暗游戏背景上进行开发版视觉检查。
- [机械迁移内部网格可能破坏游戏坐标语义] → 只迁移页面大区块、同级卡片和常规表单组，业务网格保持原实现并纳入回归测试。

## Migration Plan

1. 将当前主规范中的未提交试点差异完整对应到本 change 的 delta specs，实施期间不丢弃现有代码和测试。
2. 先完成主题作用域与公共令牌，再迁移主窗口页面级栅格，最后逐个改造业务悬浮窗。
3. 完成定向测试、完整测试、Vite 构建和开发版视觉验证后同步主规范并归档变更。
4. 若验证失败，仅回退本 change 新增的主题挂载和页面迁移，不重置进入变更前已经存在的工作树差异。
