## Context

剧情浮窗通过 `ResizeObserver` 测量 Vue 内容，再通过 IPC 调整 Electron `BrowserWindow` 并定位独立的分割抓手。当前渲染端不区分未变化几何，主进程也会对未变化边界执行 `setBounds`；同时布局上报会立即回发相同分栏比例，形成确定性回路。

## Goals / Non-Goals

**Goals:**

- 在渲染端和主进程两侧建立幂等边界，使几何同步必然收敛。
- 保留实际内容、宽度和分栏变化的即时响应。
- 让所有浮窗按交互类型使用一致的拖动协议和光标反馈。

**Non-Goals:**

- 不改变剧情数据模型、紧凑视觉布局或 IPC 公共契约。
- 不引入通用布局框架或新依赖。

## Decisions

1. 渲染端使用单个 `requestAnimationFrame` 合并 `ResizeObserver`、状态更新和比例更新产生的测量请求。相较定时防抖，逐帧合并没有人为延迟，且适合 DOM 几何测量。
2. 分别缓存上次发送的整数高度和规范化布局快照，仅对变化部分调用现有 IPC。不依赖 Promise 完成时序，因为幂等性由同步测量值决定。
3. 分栏比例监听先规范化，与当前值相同则返回；主进程的布局上报处理不再发布比例。比例仍在初始加载、重新打开和拖动抓手时发布。
4. 主进程计算目标边界后逐字段比较，只有不同时才调用 `setBounds`。这是第二道防线，保护其他调用者不会重新引入原生 resize 循环。
5. 剧情位置抓手复用自动入库的 `createOverlayDrag` 与 `OverlayDragSession`：渲染端使用 Pointer Capture，主进程从按下时的固定起点计算位置，并在每次移动时写入规范宽高。主进程轮询屏幕指针命中抓手热区，只在命中状态变化时切换剧情内容穿透。分栏抓手保持独立的一维原生抓手，拖动期间只读取实际位置并发布比例，结束后再程序化对齐。
6. 可拖动浮窗分为两类：固定尺寸或穿透浮窗使用共享 Pointer Capture 协议；完整交互且可调整大小的价格检查浮窗使用同窗原生标题栏拖动。两类抓手统一使用 `grab`/`grabbing`，按钮等非拖动区使用 `no-drag`。
7. 制作进度浮窗从不可靠的 DOM `mouseenter` 穿透切换与原生拖动迁移到共享 Pointer Capture 协议；自动入库、商店配方控制和剧情浮窗共享同一渲染端拖动工具与主进程会话模型。

## Risks / Trade-offs

- [DOM 几何小数抖动可能造成额外上报] → 高度与原生窗口一致取整，布局字段按浏览器测量值精确比较，同一帧先合并。
- [Windows 高 DPI 下原生拖动与跨窗口同步导致坐标跳变和尺寸逐帧增长] → 使用固定起点 Pointer Capture，并在每帧从规范尺寸生成完整边界，禁止使用上一次原生取整尺寸累积计算。
- [穿透窗口的 DOM 悬浮事件不稳定] → 主进程使用屏幕坐标命中抓手热区，状态变化时才切换鼠标穿透。
- [过度去重可能吞掉真实更新] → 缓存仅在实际发送前更新，高度和布局独立判定。

## Migration Plan

无数据迁移。在开发版通过自动测试和人工打开/拖动验证后随正常代码发布；回滚时只需回退渲染端与窗口管理的幂等处理。
