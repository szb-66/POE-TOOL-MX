## Context

现有 `operationDelay.js` 已集中保存四组用户设置和默认值，但调用方分别手工挑选字段，导致线协议不完整。部分持续功能只在初始化时同步，商城配方读取模块独立延迟；Python 脚本还在输入边界使用固定数字或 `max()` 下限。自动化是安全敏感路径，统一时序不能削弱前台验证、输入配对释放和结果确认。

## Goals / Non-Goals

**Goals:**

- 复用现有四组设置形成唯一完整协议和唯一序列化入口。
- 让每条游戏输入链路按相同语义消费配置，并支持安全边界上的运行时更新。
- 通过行为测试证明实际脚本而非中间管理器使用了配置。

**Non-Goals:**

- 不把战斗业务间隔、轮询频率、网络限流、UI 防抖和进程生命周期开放为全局时序。
- 不改变识别算法、自动化重试次数、坐标/DPI/前台门禁或停止策略。
- 不引入新依赖，不打包发布。

## Decisions

### 1. 扩展现有工具，不建立第二套配置模型

在 `operationDelay.js` 增加完整对象规范化与 Python snake_case 序列化；保留现有单字段规范化函数供迁移和兼容调用。所有管理器和脚本生成器只通过完整入口构造线协议。

备选方案是新增嵌套 `automationTiming` 持久结构，但会制造迁移和双写，本变更不采用。

### 2. 物理输入和结果等待分层

`operationDelayMs` 只负责移动后悬停；四个物理字段始终生效。剪贴板、画面、页签和存仓属于结果等待：自适应模式观察已有信号并以上限兜底，固定模式使用对应固定字段。没有可靠信号时仍使用对应固定字段，不退回裸数字。

### 3. 单一运行时更新入口，离散动作使用快照

新增完整时序更新 IPC，由设置提交一次规范化对象并分发给已注册的持续消费者。旧背包单字段 IPC 转发到同一入口。已经启动的单次脚本不热改内存；下一次启动读取全局设置。长期战斗进程通过现有原子配置文件更新，从下一循环读取新时序。

### 4. 商城配方旧字段只读兼容、执行时忽略

规范化旧商城配置时不再输出独立 `operationDelayMs`，界面不再展示该控件；执行始终读取全局时序。旧本地字段不迁入全局，避免静默覆盖用户当前统一设置。

### 5. 裸等待按语义审计而非全部删除

动作完成等待必须映射到协议字段。前台/OCR/剪贴板轮询粒度、错误提示停留、子进程启停等内部计时改为有名称的内部常量并纳入测试白名单，避免错误地让安全和生命周期依赖用户可设的 0ms。

## Risks / Trade-offs

- [用户把物理时序设为 0 可能降低游戏输入可靠性] → 保留现有安全确认、失败停止和明确字段说明，不暗加下限。
- [跨多个持续消费者同步可能部分失败] → 先规范化和同步，失败时不提交新的全局修订；下一次启动仍以持久化成功修订覆盖运行时。
- [自适应结果信号并非所有动作都存在] → 仅复用可靠的剪贴板/OCR/截图信号，没有信号时使用用户配置的固定结果等待。
- [工作区已有重叠改动] → 实施时逐文件合并现状，不回退用户修改，并在完成后检查失败尝试遗留。

## Migration Plan

1. 添加完整协议 helper 和兼容转发，不改变持久化字段。
2. 逐条接入管理器、脚本生成器和 Python 动作边界。
3. 移除商城配方独立延迟的读取、保存和界面入口；旧字段留在已有本地 JSON 时被忽略。
4. 更新设置布局和运行时同步，执行受影响测试、全量测试、Vite 开发转换与 OpenSpec 严格校验。
5. 若需回滚，恢复各调用方旧字段构造；持久化结构未变化，无数据回迁。
