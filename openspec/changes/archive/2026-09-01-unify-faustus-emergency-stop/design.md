## Context

浮士德页面目前直接调用领域 store 的停止方法，同时 Electron 主进程的全局紧急停止协调器已经包含浮士德 manager。现状的安全链路具备统一停止能力，但页面仍暴露第二个用户入口，且主规范未把浮士德写入全局紧急停止覆盖列表。参见 proposal.md 与两份增量规格。

## Goals / Non-Goals

**Goals:**

- 让浮士德页面只提供启动操作，并清晰展示实际可用的全局紧急停止快捷键。
- 保持全局紧急停止对浮士德 manager 的幂等终止、输入释放和自动化锁释放行为。
- 用 UI 与集成测试锁定“无专用停止按钮、全局停止仍覆盖浮士德”的契约。

**Non-Goals:**

- 不移除 manager、主进程停止 IPC 或应用退出清理所需的内部停止能力。
- 不改变全局快捷键的默认值、作用域、持久化或注册方式。
- 不改变浮士德识别、改价、配置和错误恢复逻辑。

## Decisions

### 1. 页面移除专用停止按钮，改为只读快捷键提示

运行控制区保留“开始改价”和进度，移除直接调用浮士德 store 停止方法的按钮。在同一区域显示设置 store 中当前生效的全局紧急停止快捷键，使用户不必离开页面确认停止方式。

选择该方案是因为停止入口本身是跨模块安全能力，页面只应解释入口而不复制终止动作。备选方案是在页面按钮上调用全局紧急停止，但这仍会保留第二个视觉停止入口，并可能让用户误以为只停止浮士德，因此不采用。

### 2. 保留内部停止 API，不作为页面操作暴露

浮士德 manager 的 `stop` 继续由全局紧急停止协调器、应用清理和安全失败路径使用。renderer 侧现有封装可以暂时保留以避免扩大兼容性改动，但页面和用户可见帮助不得把它作为独立停止方式。

选择保留内部停止能力是为了确保异常和退出路径仍可释放输入与锁。备选方案是删除全部浮士德停止 IPC，但会把兼容性清理与本次 UI/契约统一混在一起，且不能替代主进程必须具备的停止能力。

### 3. 在全局协调器层验证覆盖，而不是复制停止逻辑

实现继续复用现有全局紧急停止协调器中的浮士德 manager action。测试应验证浮士德处于运行态时会被计入停止结果，同时单项失败、重复触发和空闲触发的既有行为不回退。

## Risks / Trade-offs

- [用户未记住快捷键时找不到停止入口] → 在运行控制区持续显示当前快捷键，并在运行态保持提示可见。
- [快捷键设置状态尚未加载] → 复用设置 store 的规范化默认值，不在页面硬编码第二套默认逻辑。
- [只删按钮却破坏异常清理] → 保留主进程 manager 停止能力，并用紧急停止与 manager 测试覆盖输入和锁释放。

## Migration Plan

1. 更新页面与 UI 测试，移除专用停止并显示全局快捷键。
2. 补强全局紧急停止测试，明确验证浮士德运行态。
3. 运行受影响的单元/集成测试、Vite 构建与开发版浏览器验证。
4. 若需回滚，仅恢复页面按钮和旧规范文案；主进程统一停止链路无需回滚。
