## Context

制作主窗口与制作悬浮窗是独立渲染进程。当前冻结批次只保存在主窗口 Store 和生成后的 Python 脚本内，悬浮窗收到的事件只含进度数字与当前项；异常后从悬浮窗调用公共启动函数时，其本地批量 Store 没有扫描快照，因而无法重建原批次。现有 Python 进程已经维护 `batch_completed_ids` 和当前目标，但未将其形成可由下一进程消费的恢复检查点。

## Goals / Non-Goals

**Goals:**

- 以主进程运行态作为跨窗口批次恢复事实来源。
- 在不重复已完成输入的前提下，使用最新制作配置安全继续原批次。
- 任何恢复均先核验全部未完成目标，并沿用原通货会话。

**Non-Goals:**

- 不跨应用重启持久化恢复检查点。
- 不根据相同底材、相近格子或显示名称猜测替换目标。
- 不允许用户主动停止后继续，也不改变地图恢复协议。

## Decisions

### 1. 主进程持有规范化运行期检查点

批量首次启动时，renderer 在现有脚本执行请求旁提交经过白名单裁剪的批次上下文；主进程验证 `batchId`、`scanId`、指纹、唯一目标 ID、格子、尺寸和位置字段后深拷贝保存。主进程根据可信 Python 子进程发出的目标开始、目标完成和异常事件更新 `currentItemId` 与 `completedIds`，并向主窗口和悬浮窗暴露只读快照。

选择主进程而不是任一 Pinia Store，是因为两个窗口没有共享内存，且主进程掌握进程生命周期与可信事件边界。检查点不写入磁盘，应用退出自然失效。

### 2. 恢复配置由原目标和最新设置组合

恢复请求从主进程取得检查点，公共启动函数忽略悬浮窗空的扫描 Store和当前类别勾选，使用原目标集合并排除 `completedIds`。目标的扫描内身份和顺序保持冻结；绝对鼠标位置依据目标格子与最新背包网格重新计算。词缀目标、通货坐标、仓库选择、DPI 和时序均读取点击当下设置。

相比重放旧脚本，这允许用户修正配置；相比重新扫描，这不会改变原批次成员或重复已完成目标。

### 3. Python 以完整成员和已完成集合恢复

恢复脚本继续携带原完整目标列表，并以 `completedIds` 初始化完成集合。总数始终等于原成员数；身份预检与正式循环过滤已完成 ID，因此失败项自然成为第一个未完成目标。每次目标完成后立即发布带完成集合的检查点事件，后续再次异常可从新边界恢复。

身份预检仍早于仓库页选择、固定通货预检和正式制作。恢复失败不会清除旧检查点；只有新扫描、正常完成、主动停止或新批次替换会清除。

### 4. IPC 只传递恢复所需白名单

新增批次恢复读取与清除操作，只接受主窗口或当前制作悬浮窗 sender。快照只含批次标识、扫描标识、指纹、最小目标身份、完成 ID、当前 ID、通货会话和可恢复状态，不含完整复制文本、词缀结果、账号字段、Cookie 或路径。

### 5. 浮层优先使用可信恢复资格分类

浮层加载和停止时读取主进程检查点。存在可恢复批次时显示继续、重新扫描和关闭；不存在时沿用单件或地图重试。批量继续沿用现有并发门禁；返回重新扫描先清除检查点，再恢复主窗口。这样即使启动阶段在首个批量进度事件前失败，也不会误判为单件。

## Risks / Trade-offs

- [恢复期间用户移动或替换未完成物品] → 对全部未完成目标执行无损身份预检，失败时零通货输入并保留错误。
- [renderer 伪造检查点字段] → 主进程按固定 schema、数量、边界和唯一性验证，并仅接受受信窗口 sender；运行进度只由当前 Python 子进程事件推进。
- [最新配置改变制作结果] → 目标成员固定但制作配置明确采用点击时最新值，校验失败保留检查点供再次修正。
- [异常发生在进度事件之前] → 主进程在创建 Python 进程前建立初始检查点，浮层不依赖本地批量事件判型。
- [多次修复残留单件旁路] → 保留 `singleItemOnly` 只服务无批量检查点的真实单件重试，并增加互斥回归测试。

## Migration Plan

1. 增加纯检查点规范化与生命周期测试，再接入主进程运行态和受限 IPC。
2. 扩展脚本配置、事件和恢复过滤逻辑，再接入公共启动服务。
3. 更新浮层批量继续与重新扫描入口，验证跨窗口失败路径。
4. 在开发版运行定向与完整测试；不打包。回滚时移除恢复 IPC 和分支即可恢复强制重新扫描行为。
