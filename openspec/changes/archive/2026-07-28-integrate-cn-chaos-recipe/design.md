## Context

应用使用 Electron 28、Vue 3、Pinia 和 Python 辅助脚本，已有全局快捷键、屏幕区域选取、DPI 换算、透明浮窗和前台窗口校验能力。ChaosRecipeEnhancer 是 GPL-3.0 的 .NET/WPF 项目，其国际服 OAuth 客户端不能用于国服；国服站点的相关路由存在但没有公开契约，因此网络层必须隔离并允许新旧响应适配。

## Goals / Non-Goals

**Goals:**

- 在现有商城页提供国服混沌配方统计、缺件、浮窗高亮和分标签页取件。
- 支持网页登录和手动会话令牌，令牌不进入渲染层持久化或日志。
- 将国服新版/旧版仓库响应归一化为稳定内部模型。
- 复用现有坐标、DPI、快捷键和 Python 进程基础设施。

**Non-Goals:**

- 不支持其他商店配方、公会/特殊仓库页、掉落过滤器修改或自动切换仓库页。
- 不对国服未公开接口做持续盲探测，不读取游戏内存。
- 不自动采集或保存 QQ 密码。

## Decisions

1. 使用 `persist:poe-cn-auth` 独立 Electron Session。网页登录窗口关闭 Node 集成并限制导航域；手动令牌直接写入同一 Session 的 `POESESSID` Cookie。主进程通过 `/api/profile` 验证，会话状态只向渲染端暴露脱敏摘要。
2. 网络层实现两个显式 Provider：优先 `/api/stash/{league}` 新接口，失败后使用 `/character-window/get-stash-items` 旧接口。一次成功后缓存 Provider；401 使会话失效，429 按 `Retry-After` 退避。
3. 内部模型仅保留配方需要的字段。类别优先使用 API category，否则解码 CDN 图标路径；国服 CDN 域名不参与分类判断。
4. 配方引擎采用纯 JavaScript 无副作用函数，先用 60–74 物品为每套建立混沌配方保底，再用 75+ 补齐，最后以跨页和格子距离排序取件计划。
5. 浮窗使用独立 BrowserWindow。普通仓库为 12×12，大型仓库为 24×24；用户分别保存物理像素矩形，坐标由 API 格子换算。
6. 自动取件使用打包的独立 Python 脚本。脚本在每次点击前检查游戏前台、界面模板并复制物品文本核对目标；跨仓库页时主进程暂停，由用户切页后继续。
7. 许可证切换为 GPL-3.0-or-later，并保留 ChaosRecipeEnhancer 归属。界面仍按本项目风格实现，不嵌入 WPF。
8. 自动取件子进程在首件物品验证前恢复并激活游戏窗口；任何终止路径都关闭不可交互浮窗。仓库手动刷新禁用 HTTP 缓存，现代详情为空或只有少量不可识别条目时只对照一次旧版详情，并选择物品数更多的结果。
9. Win32 前台激活只对 `IsIconic` 的最小化游戏窗口调用 `SW_RESTORE`；普通窗口和最大化窗口不得调用会重置布局的恢复操作。

## Risks / Trade-offs

- [国服接口无公开契约] → 新旧 Provider、结构验证、匿名快照测试和明确的不兼容错误。
- [会话令牌泄漏] → 专用 Session、禁止日志记录、渲染层不持久化、注销时清理 Cookie 和缓存。
- [仓库 API 限流] → 单次手动刷新、Provider 缓存、响应头退避和并发去重。
- [错误坐标取走其他物品] → 界面校准、每件点击前剪贴板核验、前台检查、跨页暂停和紧急停止。
- [批量输入可能违反第三方工具规则] → UI 明示风险并要求用户主动启动；功能不在后台或定时自动触发。
- [GPL 改变分发义务] → 更新许可证、README 和上游声明，并随构建产物分发许可证。

## Migration Plan

1. 先引入纯配方模型、Provider 和契约测试，不接入 UI。
2. 加入专用认证 Session、IPC 和商城页配置；真实账号验证接口后保存匿名响应快照。
3. 加入浮窗、校准和取件脚本，先以模拟计划验证，再进行真实仓库人工验收。
4. 更新许可证和打包资源，运行全量测试与构建。
5. 回滚时可移除新商城标签和 IPC 注册；现有商店正则数据结构保持不变。

## Open Questions

- 国服真实账号返回的新接口响应是否与国际服 OAuth 仓库结构完全一致；实现通过运行时结构校验解决，不阻塞旧接口回退。
