## Context

现有 schema v2 将共享 `WeaponCasterDamagePrefix` 的法术、火焰、冰霜和闪电伤害按效果签名拆成了多个外层项。这些效果应作为同一 Mod Family 的内部分支，共同形成父项总权重；每个分支内仍保留自己的等级和权重。

POEDB 的 `ModsView` 载荷已经提供 Mod Group、每条记录的文本、标签、需求等级、权重和来源分区；`/cn/Modifiers` 提供目录层级；工艺台表格和 `master` 记录还共享稳定的 hover URL。修复应复用这些来源字段，而不是增加更多中文名称特判。数据仍需支持内置离线快照、运行时原子更新和 Worker 规划。

## Goals / Non-Goals

**Goals:**

- 在当前支持的装备范围内复现 POEDB 的分类路径和特殊底材词缀配置。
- 将“目标效果”与“实际获得来源”分离，允许规划器自动比较天然和工艺台方案。
- 精确保留效果、标签、等级、权重、数值、适用条件和工艺成本。
- 保持 Mod Group 冲突、词缀容量、概率抽取和快照回退正确。
- 让目标选择界面完整展示数据且符合左已选、右待选的操作方式。

**Non-Goals:**

- 不新增药剂、地图、夺宝装备、精髓、化石或其他尚未支持的做装体系。
- 不把 POEDB 中文名称当作稳定标识，也不按中文同名直接删除合法底材。
- 不迁移旧 schema v2 活动快照或持久化中的临时页面选择。

## Decisions

### 1. 使用目录路径和词缀配置标识底材

生成器从 `/cn/Modifiers` 的导航提取受支持目录路径，并把 `categoryPath` 与 `modifierProfileId` 写入 `BaseItem`。普通物品共享类别配置；召集法杖、骨环等特殊入口绑定其专属页面和基础类型。词缀生成条件首先匹配配置 ID，再校验物品类别、标签、物品等级和势力。

这比继续扩充 `inferTags` 更可靠，因为召集法杖与普通法杖拥有相同 Item Class，但不同词缀池。手工枚举仅作为受支持顶层范围白名单，不再定义 POEDB 内部层级。

### 2. 使用父项、效果分支和等级三层模型

schema v3 使用 `ModifierFamily -> ModifierGoal -> ModifierTier`。父项 ID 由词缀配置、来源范围、前后缀和 Mod Family 生成；目标 ID 再结合规范化效果签名生成。CraftState 仍保存具体目标、等级、Mod Group 与来源。

效果签名只用于父项内部区分精确目标，不再拆分外层项。用户选择具体分支和最低等级；同父项的其他分支不会误判为目标达成，两个分支仍不能同时作为可达目标。

### 3. 阶级元数据按原始记录保存

天然记录按需求等级由高到低编号 T1、T2；每阶保存自己的 `weight`、数值向量、原始文本和 `{ id, label }` 标签。目标级标签是所有阶级标签的稳定有序并集，只用于搜索和摘要；概率池和标签工艺使用具体阶级标签，避免并集扩大实际生成条件。

若一个效果没有天然版本，则按工艺台数值由强到弱形成可选等级。天然与工艺台同时存在时，以天然阶级作为用户门槛，工艺选项不伪装成相同序号。

查询时保留所有等级，并为每条记录计算 `available`。父项 `subitemCount` 统计全部等级行；`totalWeight` 只汇总当前物品等级可天然生成的记录。随机生成先按父项总权重抽取，再在父项内按等级权重抽取具体结果。

### 4. 通过 hover 标识连接工艺记录和成本

解析 `master` 分区为工艺词缀候选，再以记录的 hover URL 与 `/cn/Crafting_Bench` 第一张表中的 `data-hover` 精确连接。只有成功连接的记录才成为可执行工艺选项，并带上表格中的成本、适用类别和解锁信息；元工艺继续保留规范定义。

规划器为目标查找效果签名一致的工艺选项。工艺数值向量的每个最低值都不低于目标阶级对应最低值时才满足门槛；复合效果必须所有分量达标。这样无需用户选择来源，也不会用较弱工艺冒充高阶天然词缀。

### 5. 明确处理重复与同名底材

生成阶段排除 source ID 或元数据标记为 Royale、测试、占位和废弃的基础类型。稳定 ID 不变的合法基础类型全部保留；若多个合法底材具有相同中文名，生成唯一 `displayName`，附加需求等级和必要的基础属性摘要。搜索结果按 ID 去重并展示 `displayName`，因此不会出现无法区分的重复项。

### 6. 升级查询结果与界面但保持规划请求

词缀搜索返回父项及嵌套目标/等级，规划请求仍为 `{ goalId, minTierId }`。页面三个主模块全宽纵向排列，目标模块内部在宽屏保留左已选、右待选。schema v2 活动目录加载时回退内置 v3。

数据更新、任务 ID、Worker 取消和结果事件协议保持现状。schema v2 活动目录加载时视为不兼容并回退内置 v3，等待用户手动更新。

## Risks / Trade-offs

- [POEDB 导航或 hover 结构调整] → 使用真实结构 fixture、字段级错误和最小数量/关联率验证；失败更新不得激活。
- [效果签名误合并] → 效果签名只在 Mod Family 父项内区分目标，并为共享父项、复合词缀和静态文字差异建立黄金测试。
- [工艺台数值与天然 T 级没有一一对应] → 使用逐分量最低值的保守门槛，结果可能少推荐边界工艺，但不会高估可达性。
- [合法同名底材显示名称较长] → 仅在发生同名碰撞时增加限定信息，稳定 ID 和搜索关键词仍保留原名。
- [schema v2 用户快照暂时失效] → 永久保留内置 v3 回退，状态栏提示重新更新，不删除用户文件。

## Migration Plan

1. 扩展解析 fixture 与 schema v3 模型，先建立父项、目标、等级和工艺关联的单元测试。
2. 调整生成器、运行时更新器、仓库查询和内置快照；验证旧快照只触发安全回退。
3. 迁移 CraftState、请求校验、概率池与策略生成，移除来源策略和硬编码工艺成本。
4. 更新规划页面、说明和 OpenSpec 文档，完成全量测试、生产构建及一次实时数据生成。
5. 若发布后新目录不可用，可回退应用版本及其内置 v1 快照；用户目录不会被新版本破坏。

## Open Questions

无。支持范围、来源行为、工艺台等级判定和同名底材处理均已确定。
