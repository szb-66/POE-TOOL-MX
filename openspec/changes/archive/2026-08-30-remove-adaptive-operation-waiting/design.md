## Context

见 proposal.md。当前自动化时序协议同时携带 `adaptiveTiming`、`adaptiveTimeoutMs` 与 `fixedTiming`；不同 Python 消费者据此选择有界轮询或固定等待。此前 `simplify-automation-timing-configuration` 曾删除全部高级时序并改为内部轮询，但开发版验收因整体变慢被否决并回退。本变更只删除自适应分支，保留现有物理输入与固定结果等待配置。

## Goals / Non-Goals

**Goals:**

- 让结果等待只有一条可复现的固定时序路径。
- 从界面、持久化、导入导出、IPC 和 Python 载荷中彻底删除两个自适应字段。
- 保留当前 `operationDelayMs` 和全部 `fixedTiming` 字段及其用户配置能力，并采用用户确认的新默认值。
- 对旧配置容错读取，并在下一次保存或导出时净化废弃字段。

**Non-Goals:**

- 不删除或内置化四项物理输入与四项结果等待。
- 不重新引入此前失败方案的自动检测、单字段协议或内部事件轮询。
- 不改变制作事务证据、错误码、自动化安全门禁或模块业务节奏。
- 不打包、安装或发布。

## Decisions

### 1. 当前时序模型采用 `{ operationDelayMs, fixedTiming }` 封闭投影

设置规范化、持久化、导入导出、渲染到主进程以及主进程到自动化宿主都显式投影这两个字段。Python 边界只生成 `operation_delay_ms` 与 `fixed_timing`，不再生成固定值为 `fixed` 的 `timing_mode`，避免保留一个已经没有分支意义的伪协议字段。

未选择只隐藏界面，因为旧字段继续流经运行时会让自适应行为仍可被旧配置或对象展开重新启用。

### 2. 结果确认始终先完整等待对应固定字段

剪贴板/空格、页签、存仓和画面变化分别使用 `clipboardConfirmMs`、`stashTabSettleMs`、`stashSettleMs` 与 `patchVerifyMs`。消费者在对应等待结束后读取或验证结果，不因提前检测到结果而缩短等待；需要多次验证的流程在每个既有验证检查点使用对应固定等待，并保留原重试次数与错误结果。

未将现有轮询改成固定次数的短轮询，因为那仍属于自适应提前完成；也不新增统一固定延迟，以免重新制造与四个现有字段重叠的配置。

### 3. 物理输入时序与结果等待保持同一 `fixedTiming` 结构

继续使用现有八字段结构，避免这次移除自适应行为时改动无关的用户数值、跨进程字段名和输入安全边界。界面删除条件显示，四项结果等待改为始终展示。

### 4. 迁移使用版本提升与白名单净化

提升 `operationTimingVersion`。读取当前设置和导入旧备份时忽略 `adaptiveTiming`、`adaptiveTimeoutMs`，保留规范化后的 `operationDelayMs` 与 `fixedTiming`；保存、重置和导出都只写当前结构。这样既兼容旧数据，也防止对象展开让废弃字段回流。

### 5. 自动检测结果删除自适应上限推导

保留当前无副作用检测、安全预检、实测字段和其他固定时序推导，只删除 `adaptiveTimeoutMs` 的输入、推荐证据、结果行、应用与撤销快照。应用与撤销仍通过完整当前时序事务一次完成。

### 6. 对失败方案和旧分支做负向审计

实现结束时同时搜索自适应字段、Python 模式分支、界面条件显示和此前失败单字段方案可能遗留的内部轮询代码。仅删除已无消费者的自适应专用代码；保留业务轮询、OCR、前台检测和安全超时等非结果自适应逻辑。

### 7. 新默认值只用于默认与缺失回退

当前默认表固定为：`operationDelayMs=40`；`modifierSettleMs=20`、`keyHoldMs=15`、`buttonHoldMs=15`、`releaseSettleMs=10`；`clipboardConfirmMs=10`、`stashTabSettleMs=10`、`stashSettleMs=10`、`patchVerifyMs=10`。新建设置、字段缺失或无效、恢复默认使用该表；已有有效用户值原样保留，不因版本升级被替换为新默认值。旧三字段和 80ms 旧默认迁移继续沿用既有兼容路径，但最终默认回退值改为 40ms。

未选择把所有现有用户值强制迁移到新默认，因为“默认值”不应覆盖已保存的有效自定义设置。

### 8. 九个字段共用可访问的问号说明模式

每个输入标签右侧复用同一问号入口与说明浮层表现：鼠标悬停和键盘聚焦展示相同内容，入口提供能识别字段名的无障碍名称。说明文案由字段元数据集中维护，逐项描述“等待发生在什么动作之后、什么动作之前”及主要消费者，避免模板中散落互相矛盾的文案。

未使用区域底部的统一说明段落作为替代，因为用户要求在每个延迟类型标题旁就地查看，且逐项边界不同。

## Risks / Trade-offs

- [固定等待无法在结果提前出现时节省时间] → 这是本次显式行为选择；保留四个独立字段和自动检测建议，允许按实际机器调整。
- [旧对象展开让废弃字段重新进入协议] → 所有存储与跨进程边界使用白名单投影，并增加负向载荷测试。
- [把业务轮询误删为自适应等待] → 按四类结果等待消费者清单逐项迁移，非输入计时与安全失败超时保持独立。
- [不同消费者对同一固定字段重复等待] → 定向测试审计动作边界，确保每个既有结果检查点只消费一次对应字段。
- [10ms 结果等待在部分机器上可能不足] → 保留每项用户配置和自动检测建议，默认值不覆盖已有有效设置，并在开发版逐链路验收失败行为。
- [问号文案与实际消费者漂移] → 从统一字段元数据渲染并以字段到说明的映射测试约束九项内容。
- [与当前大量未提交改动重叠] → 实施时逐文件检查现有差异，只修改自适应时序相关片段并精确暂存。

## Migration Plan

1. 先更新新默认表、时序规范化与迁移测试，提升版本并建立 `{ operationDelayMs, fixedTiming }` 白名单，同时证明已有有效值不会被覆盖。
2. 收敛设置、导入导出和跨进程协议，再迁移 Python 消费者到固定结果等待，避免半迁移状态。
3. 删除设置页自适应项和自动检测中的自适应上限结果，四项固定等待改为始终显示，并为九项延迟增加统一可访问问号说明。
4. 运行定向测试、完整测试、开发构建、严格 OpenSpec 校验和仓库级负向审计；随后只在开发版手工验收，不打包。
5. 回滚时整体恢复协议版本、两个字段、界面与所有消费者分支，不能只恢复界面。
