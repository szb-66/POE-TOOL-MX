## Context

当前生成的 Python 制作脚本使用 `explicitMods` 数组长度判断魔法物品是否只有一个词缀，但该数组按效果文本行展开；解析器同时提供了按词缀聚合的 `modifiers` 和 `detailedMods`。脚本在循环内有条件增幅，成功收尾又会无条件增幅，两个入口的行为不一致。

## Goals / Non-Goals

**Goals:**
- 让初始检查和改造循环共享同一套单词缀判断与增幅后重读语义。
- 以现有解析结果完成修复，不改变预设、IPC 或通货预检接口。

**Non-Goals:**
- 不重构通用物品解析数据模型。
- 不改变富豪石、崇高石、插槽或古灵制作行为。

## Decisions

1. 在生成的 Python 词缀制作代码中增加实际显式词缀计数辅助逻辑。存在结构化 `modifiers` 时统计 `prefix`、`suffix`、`fractured`、`crafted` 等占位记录；没有结构化记录时回退到 `detailedMods`，最后回退到 `explicitMods`，以兼容旧解析结果。
2. 增加单一的“需要时增幅并返回最新结果”辅助流程，由初始检查和每次改造后的判断共同调用。成功使用增幅后必须重新读取、等待解析并返回新结果；失败返回明确失败状态，调用方不得继续报告完成。
3. 从成功收尾函数移除增幅，仅保留富豪石或崇高石等真正的达标后步骤。这样每轮最多消耗一次增幅，且使用发生在达标判断之前。
4. 回归测试通过 Vite SSR 生成真实 Python 代码，再用项目 Python 运行时和桩函数执行生成的词缀流程，以覆盖生成器与运行逻辑的实际接缝。

## Risks / Trade-offs

- [旧格式没有结构化词缀边界时仍只能按文本行回退] → 保持现有兼容行为；开发版自动解析优先使用结构化结果，测试覆盖回退路径。
- [结构化类型集合遗漏占位词缀] → 明确覆盖天然前后缀、破裂和工艺类型，并以双词缀测试约束不产生误增幅。
- [初始检查顺序变化导致多消耗一次通货] → 仅在用户明确启用增幅且实际单词缀时执行，符合已确认的产品语义。
