> **实施结论（2026-08-30）**：下述设计已在开发版验收中失败并撤销。当前运行时恢复 v1.2.2 制作流程；除非用户重新提出并确认新方案，不再继续实施本设计。

## Context

见 `proposal.md` 的 Why。当前生成脚本同时承担输入、复制证据、文本历史、解析请求、结果文件改写、发布等待和业务循环；Electron 也会改写同一结果文件，因此一个动作跨越多套隐式状态。当前工作区还有其他未提交功能，实施时必须精确编辑制作协议相关文件并保留无关改动。现有通货预检、前台/DPI/坐标门禁、输入释放、紧急停止、恢复检查点和账单事件已经具备独立测试，不需要重造。

## Goals / Non-Goals

**Goals:**

- 让动作前/动作后结构化快照成为制作结果的唯一事实来源。
- 让一个事务只有一个入口、一个通货动作和一个可确认终态，所有业务路径只消费已确认快照。
- 让 Python 与 Electron 对文件协议各自拥有唯一写入文件，并用复合标识隔离会话、事务和解析请求。
- 把复制读取、解析传输和业务动作恢复拆成互不混淆的预算。
- 删除旧历史哈希、`stable`/`suspicious`、布尔放行、候选自改写发布及模板旁路，而不是保留双轨实现。
- 在生成脚本、真实临时目录协议和业务推进边界建立可重复的 TDD 回归。

**Non-Goals:**

- 不改变制作策略、词缀匹配算法、地图/海图条件、通货预检或账单计算。
- 不改变全局自动操作等待、自动时序校准的测量与推荐算法、用户配置、持久化模型或公开 Electron API；共享通货动作消费现有校准结果中的目标稳定边界。
- 不代替用户操作游戏窗口，不打包、不安装、不发布。
- 不在本变更中自动同步或归档任何 OpenSpec；归档必须另行得到用户确认。

## Decisions

### 1. 新建独立事务协议并在迁移完成后删除旧观察协议

新增一份生成期共享的 Python 事务协议，向装备和地图/海图模板提供 `read_baseline` 与 `run_currency_transaction` 两个领域入口。事务状态固定为：

`baseline-ready → action-applied → snapshot-ready → transition-validated → commit-sent → publication-confirmed`

任一步只能转移到下一状态或 `failed/cancelled`，失败终态不可恢复为同一事务。模板负责决定“下一种通货/目标条件”，协议负责一次动作的输入、读取、验证和提交。首次读取只建立 baseline，不伪造一次无通货事务。

不在旧 `crafting_observation_protocol.py` 上继续改名或包一层适配，因为它的 session 数据结构本身包含文本历史、pendingHash 和 stable 推断。迁移期间测试可同时加载新旧生成片段，但最终生成脚本只能内联新协议；全部调用点切换后删除旧片段及其专用测试。

替代方案是修正 `validate_currency_postcondition(stable=...)`。它能处理本次截图，却仍让跨事务文本分类控制业务验证，无法满足用户要求的整体重整。

### 2. 事务只比较规范化结构化快照

事务把解析结果规范化为领域相关 `CraftingSnapshot`。装备快照只包含当前制作策略需要的稀有度、鉴定/腐化/不可修改标记、显式词缀结构、插槽/连接/颜色和古灵隐式；物品类别、基底、名称和物品等级不用于装备身份校验或结构指纹。装备目标由固定坐标、当前复合请求标识和本次新鲜复制证据限定。地图/海图快照另行包含当前格位和策略需要的地图阶级、区域等级及制作字段。地图统计、requestId、发布标记、显示文案等传输或 UI 字段不参与动作比较。

每种通货拥有一个纯迁移策略，输入为 `(beforeSnapshot, afterSnapshot)`，输出限定为 `confirmed-change`、`candidate-stable`、`pending` 或带稳定错误码的 `invalid`。必须变化策略同时验证 before 与 after；例如重铸必须是“before 为魔法/稀有，after 为普通且显式词缀为空”，而不是只看 after 或文本是否重复。

允许无可见变化的通货先比较结构化指纹：与 before 不同且目标合法时可直接确认；与 before 相同时保存为当前事务的第一个稳定候选，只有第二个新鲜快照指纹相同才确认。稳定候选只存在于当前事务内，不进入跨事务缓存。

替代方案是比较剪贴板全文。全文包含名称、展示顺序和版本文案，且同一合法状态可以跨循环重复，不能表示动作因果。

### 3. 文件协议 v2 使用单写入方命令/结果通道

保留现有两个临时文件路径以避免扩大部署面，但重定义其所有权：

- Python 唯一写入请求文件，写入完整 envelope。
- Electron 唯一写入结果文件，写入完整 response。

命令 envelope 至少包含 `protocolVersion: 2`、`commandType`、`commandId`、`sessionId`、`transactionId` 和按命令需要提供的 `requestId`。命令类型：

- `parse`：携带一次已捕获文本；Electron 返回候选并缓存规范化解析结果。
- `commit`：只引用已缓存候选的复合标识，不携带可伪造物品结果；Electron 成功发送面板后返回 publication ack。
- `complete-target`：只在地图/海图目标终态后携带规范化累计统计，Electron 校验当前会话并返回 stats ack。

结果 response 使用 `candidate`、`publication-ack`、`stats-ack` 或 `error`，并回显全部复合标识。Electron 每个 session 只保留当前事务所需候选，开始新事务后清除前一事务候选；停止监听、新 session 或协议不兼容时清空全部状态。

Python 在同目录临时文件写完后原子替换请求文件；Electron 监听临时目录中的请求文件名以获得低延迟通知，同时每 10ms 主动读取最新请求。Electron 原子替换结果文件，Python 每 10ms 主动读取最新 response。两侧只在完整 JSON 成功解析和 envelope 校验通过后按 commandId 去重，空/损坏/中间态不进入去重基线。解析、提交和统计 response 的单次等待上界均为 2 秒；动作后首次读取固定等待 200ms，后续读取固定间隔 50ms。以上内部调度均不读取 `operationDelayMs`，Python 不额外引入文件监听依赖。

Electron 协议状态保存当前 session 的候选、已发布复合标识和最后一次 `complete-target` 确认的累计地图统计。脚本退出或停止消息从该状态读取最后确认统计，不再把随每条 response 覆盖的结果文件当作统计存储。

替代方案是继续让 Python 把 candidate 改写成 publish=true。该方案有两个写入方，并要求 Windows 必须报告 candidate→commit→ack 的快速连续改写，正是此前竞态来源。

### 4. 会话、事务和请求标识各自只有一个作用域

`sessionId` 在每次脚本启动时随机生成并保持不透明；`transactionId` 在 baseline 后每次通货动作递增；`requestId` 在同一捕获文本的每次解析传输请求递增。`commandId` 唯一标识文件命令并用于幂等消费。

业务层不得用 requestId 推断动作顺序，Electron 也不得仅凭 requestId 发布。只有 `(sessionId, transactionId, requestId)` 完整匹配当前候选时 commit 才有效。恢复重试总是生成新 sessionId，因此旧进程的迟到回调天然失效。

### 5. 复制预算、解析预算和动作预算完全分离

一次事务的动作预算恒为一。共享动作依次执行：安全选择通货、等待选择释放、移动到目标、等待现有自动时序校准给出的目标稳定边界、复核前台/坐标/按钮释放、发送一次左键。输入 API 返回成功只表示动作已发送；只有动作后结构迁移确认成功才记录一次账单，之后绝不再进入动作函数。失败时不得通过取消鼠标悬挂通货把流程缺陷伪装为已修复。

动作后最多读取三个 snapshot。一次 snapshot 先建立新鲜剪贴板证据，再解析；若已捕获文本但解析传输失败，可对同一文本发送至多三个 parse 命令，不再 Ctrl+C。必须变化结果仍为 before 状态时，消费下一个 snapshot 读取；允许稳定结果需要第二个 snapshot 时同样消费读取预算。

读取间隔由事务协议内部的有界确认调度控制，并可由虚拟单调时钟测试；它与物理鼠标移动的 `operationDelayMs` 无关。第三次仍未确认时 fail closed，不自动追加第四次或重复通货。

自动时序校准的测量和 10ms 推荐语义保持不变；物理动作层使用校准结果中已有的目标稳定信号约束“移动到目标→左键”的边界。文件协议仍使用自身固定轮询与响应上界，二者不共享等待常量。

### 6. 业务模板只消费已确认快照

装备和地图/海图模板保留各自的策略循环，但删除所有直接 `apply_currency` 后继续、沿用旧结果、未变化直接下一颗及结果文件自行更新分支。每个分支只能调用事务入口并接收两类结果：

- `confirmedSnapshot`：可作为下一步 before 或终态判断。
- `failure`：立即接入现有异常停止与恢复检查点。

地图/海图只有当前格终态确定后才能发送 `complete-target` 并等待 ack；收到 ack 后才更新本地循环位置。富豪和每颗崇高分别调用事务入口。首次目标读取和异常恢复都调用 `read_baseline`，并在任何通货前重新执行领域条件判断。

### 7. 兼容范围通过调用审计决定，不让 v1 进入新制作流程

实施前审计结果文件协议的所有调用方。若存在非自动制作调用方仍依赖旧 envelope，可在 Electron 边界保留隔离的 v1 解码器，但 v2 session 建立后该解码器不得更新制作面板或事务状态；若没有调用方则直接删除。Python 生成的装备、地图和海图脚本不保留 v1 回退，协议不匹配时安全停止。

这避免为了未知兼容保留双轨制作流程，同时不误删其他模块确实使用的内部能力。

### 8. 验证以两个稳定边界为主

TDD 使用两个已确认边界：

1. 生成后的 Python 事务入口：注入时间、复制证据、输入动作与 v2 transport，观察通货次数、快照结果、错误码和业务推进。
2. 真实临时目录中的 Electron v2 文件协议：用子进程写命令，观察候选、显式提交、发布 ack、统计 ack、丢事件轮询和旧会话拒绝。

模板静态测试只用于证明所有通货调用点都经过事务入口以及旧协议已删除，不用私有辅助函数形状替代行为测试。开发指标只包含 session 内计数、动作类型、状态、耗时和稳定错误码，不输出文本、哈希、路径、账号或凭据。

### 9. 页面操作日志使用现有事件流和内存环形缓冲

装备制作与地图/海图沿用现有脚本事件进入 renderer 的路径，将事务阶段规范化为 `{ timestamp, phase, action, outcome, code, summary, sessionId }`。两个页面各自维护容量 100 的内存环形缓冲，只接收当前模式和有效会话的记录；第 101 条覆盖最旧记录。界面默认只在底部显示紧凑的“操作日志”展开入口，不为日志预留固定内容高度，也不得覆盖停止、重试、重新定位、关闭等现有操作；用户展开后显示可滚动日志并突出最新记录和失败结果，入口切换为收起操作。

日志不写入设置、恢复检查点或磁盘，不新增 preload/公开 Electron API。规范化层只允许安全摘要，不转发剪贴板全文、物品完整原文、路径、账号或凭据。旧会话迟到事件在进入缓冲前按 sessionId 拒绝。

### 10. 正常结果采用点击后立即探测，稳定结果保留有界证据

共享通货动作的 `move_mouse` 已经消费一次 `operationDelayMs`，移动完成后只复核前台、坐标和按钮释放，不再把剪贴板确认值作为额外目标稳定下限。发送目标左键后立即开始第一次新鲜快照读取，不预先执行固定 200ms 静置；首次快照形成合法结构变化时直接进入提交与发布确认。

必须变化但仍为动作前状态时，剩余读取预算按有界间隔继续探测；允许合法无变化的通货只有在既有安全边界后取得两份当前事务的新鲜一致快照才确认。这样正常变化路径不支付保守等待，稳定路径仍不会把过早复制的旧状态当作成功。

事务指标增加 `firstSnapshotMs` 与 `confirmedMs`，只记录相对耗时、动作类型和稳定错误码。开发版以同机 v1.2.1 为基线，正常结构变化通货从目标左键发送到事务确认的中位数不得高出 150ms；该门槛不适用于需要稳定结果证据的合法无变化路径。

## Risks / Trade-offs

- **内部文件协议一次性升级会使新旧脚本不能混用。** → envelope 带明确版本，任何不匹配在输入前失败；生成脚本与 Electron 同仓构建并由集成测试配对。
- **Electron 候选缓存增加内存状态。** → 每个活动 session 只保留当前事务必要候选，新事务、停止和重启立即清理；不持久化物品内容。
- **允许稳定通货需要第二个 snapshot，少数动作会比首次新状态慢。** → 仅 after 与 before 结构化相同时触发；这是避免把旧 tooltip 当成功的必要证据，不改变鼠标移动设置。
- **解析字段不足会比旧启发式更早停止。** → 保持 fail closed；先补齐共享解析快照字段，不回退到全文文本或继续消耗通货。
- **大范围迁移容易短期出现新旧双轨。** → 按垂直切片迁移并在最终切换前用静态审计阻止旧入口；完成时必须删除旧协议、失败尝试和重复测试。
- **当前工作区包含并行未提交改动。** → 精确编辑/暂存本变更文件，实施前后分别核对 staged、unstaged、untracked，不回滚或覆盖无关工作。

## Migration Plan

1. 先建立 v2 envelope、Electron 单写入方 transport 和真实临时目录测试，不接入游戏输入。
2. 建立 Python 事务引擎与纯结构化迁移策略，用虚拟时钟和假输入完成红绿回归；覆盖本次“历史普通地图文本重复”故障。
3. 先迁移装备 baseline、预处理和一个主循环垂直切片，再迁移增幅、富豪/崇高、插槽和古灵；每组迁移后删除对应旧旁路。
4. 迁移地图/海图 baseline、鉴定、预处理、点金/混沌/重铸、瓦尔和 `complete-target` 统计确认；验证失败格不换格。
5. 审计所有协议和 `apply_currency` 调用方，删除旧观察片段、历史哈希、stable/suspicious、候选自改写发布、双写统计及只证明旧实现的测试。
6. 运行定向测试、真实 10ms/100 次协议压力测试、完整 `npm test`、`npm run build`、`git diff --check` 和 OpenSpec 严格校验；不打包。
7. 用户在开发版重启 Electron 主进程，分别对装备、地图和航海海图进行低价值通货验收；至少覆盖重复重铸循环、允许稳定通货、富豪/崇高和瓦尔收尾，并对原地图场景连续观察至少 30 次。
8. 手工验收通过后另行请求用户确认，再同步主规范；只有用户再次明确同意时才归档本变更。已归档的旧变更不重新启用或重复处理。
9. 若速度验收未达到基线门槛，使用分段指标定位复制、解析或发布确认瓶颈，不通过缩短安全输入保持或跳过事务状态掩盖性能问题。

回滚必须以完整协议为单位：恢复旧生成脚本时同时恢复旧 Electron 文件协议，或整体撤回 v2 接入；不得只撤回提交门禁、只恢复 Python 写结果或让同一运行会话混用 v1/v2。

无。当前调用审计确认生产代码中只有自动制作生成脚本写入这两个协议文件，因此 v1 完整删除，不保留非制作兼容解码器。
