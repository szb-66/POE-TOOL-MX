## Context

`SettingsView.vue` 目前在同一个滚动容器中连续渲染十一个设置区块，区块状态分别来自现有 Pinia store、本地 ref 和 Electron 监听。项目其他业务页已使用 Element Plus 横向 Tab，因此无需引入新组件或依赖。工作区中的设置页还存在其他未提交修改，实施时必须保留。

## Goals / Non-Goals

**Goals:**

- 仅重组设置页展示层，复用现有 Tab 样式和区块实现。
- 保持隐藏分类已挂载，并在应用会话内恢复分类选择。
- 为分类归属和恢复行为留下最小可运行测试。

**Non-Goals:**

- 不拆分或重构现有设置状态、处理函数和子组件。
- 不增加跨应用重启的 Tab 持久化或路由深链接。
- 不修改设置默认值、IPC 或打包流程。

## Decisions

1. 使用一个 `el-tabs` 包裹五个 `el-tab-pane`，按已确认的任务分类移动现有模板区块。相比新增侧边导航或独立路由，这与项目现有页面一致且改动最小。
2. 不启用 Tab 的延迟渲染；各面板始终挂载，只由组件控制可见性。这样不会因切换而销毁账号、更新、识别预览和拖拽监听状态。
3. 使用 `sessionStorage` 保存白名单内的 Tab 名称。它不进入设置 store，窗口会话结束后自然清除；读取无效值时回退到 `general`。
4. 为页面滚动条保留组件引用，在 Tab 变更后调用现有滚动 API回到顶部；全局重置逻辑不接触 `activeTab`。
5. 新增一个源码契约测试覆盖分类、归属和会话逻辑，并继续运行现有直接读取设置页源码的集成测试。

## Risks / Trade-offs

- [现有源码测试依赖模板文本顺序] → 只增加 Tab 包装并保留各区块内部内容及处理函数，运行全部相关测试确认兼容。
- [隐藏面板仍占用少量运行资源] → 这是保持交互连续性的明确取舍，设置页规模无需额外懒加载优化。
- [工作区存在重叠未提交修改] → 基于当前文件增量编辑并在完成后检查差异，不还原或覆盖既有内容。

## Migration Plan

无需数据迁移。若出现问题，可移除 Tab 包装和会话级页面状态，现有 store 数据与 IPC 不受影响。
