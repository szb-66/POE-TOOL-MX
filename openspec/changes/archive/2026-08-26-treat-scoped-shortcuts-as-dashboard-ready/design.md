## Context

数据看板当前在 `useDashboard` 内同时读取快捷键注册健康、前台门禁可用性和游戏前台状态，并用嵌套条件直接构造健康项。游戏不在前台属于门禁的正常保护行为，但现有计算将其映射为 `attention`，继而影响面板颜色、系统环境汇总、诊断上下文和设置入口选择。

## Goals / Non-Goals

**Goals:**

- 将“配置和注册是否健康”与“门禁当前是否允许实际注册”分开判定。
- 让快捷键健康状态计算成为可直接覆盖状态矩阵的纯函数。
- 继续复用现有 `ready`、`attention`、`error` 和 `pending` 状态，使下游汇总、诊断与设置导航自然得到正确结果。

**Non-Goals:**

- 不改变前台门禁的实际注册、注销、延迟注册或失败回滚行为。
- 不修改主进程、前台监视器、IPC、Pinia 设置字段、持久化格式或公开接口。
- 不改变前台监视器失败时回退为无条件全局注册的现有策略。

## Decisions

### 1. 在看板状态模块中集中计算快捷键健康项

在现有看板状态模块增加一个纯函数，接收注册健康和门禁状态所需的最小字段并返回统一的 `{ status, text }` 健康项。`useDashboard` 只负责从设置 store 组装输入。

选择这一方案是因为它能直接进行行为矩阵测试，并避免为了单测挂载 Vue、Router 和多个 Pinia store。备选方案是保留 `useDashboard` 内的嵌套条件并继续使用源码正则断言，但该方式只能证明文案存在，不能证明每组输入得到正确分级。

### 2. 正常的游戏非前台状态不保留诊断原因

注册成功、门禁可用但游戏不在前台时统一返回 `ready` 和“快捷键已就绪（切回游戏后生效）”。不再把标题、进程或无前台窗口原因附加到健康项；这些仍由既有门禁状态保留供设置与底层诊断使用，但不作为首页异常。

选择统一文案可准确表达“系统正常但当前未生效”，同时避免把正常窗口切换呈现为需要用户排查的故障。备选方案是保留暂停原因但改为绿色，这仍会让用户误以为需要处理标题或进程匹配。

### 3. 通过既有状态语义修正所有下游行为

正常门禁暂停返回 `ready` 后，现有系统环境汇总将不再显示“需要关注”，诊断上下文会得到空异常原因，设置导航也会跳过快捷键项。注册失败继续返回 `error`；监视器不可用继续返回 `attention`；初始化继续返回 `pending`。

不为这些下游逻辑增加快捷键特例，避免同一状态在不同消费者中出现不同解释。

## Risks / Trade-offs

- [首页不再展示具体前台不匹配原因] → 这些信息仍保留在设置状态和底层门禁通知中；首页只承担健康摘要职责。
- [纯函数输入与 store 字段可能发生漂移] → 用完整状态矩阵测试固定输入映射，并让 `useDashboard` 仅做显式字段传递。
- [与现有未提交看板改动重叠] → 实施时基于当前工作树做最小局部编辑，不覆盖或回退已有设置导航改动。

## Migration Plan

无需数据迁移。开发版验证通过后同步 `dashboard-home` 主规范并归档变更；若需回滚，只恢复看板状态映射及对应测试，不触碰快捷键运行时机制。
