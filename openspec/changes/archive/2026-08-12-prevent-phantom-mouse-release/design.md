## Context

背包入库、普通仓库出库和君锋镇出库复用同一输入控制器。旧清理逻辑在不知道输入是否仍被脚本按住的情况下释放左右鼠标和修饰键；正常 Ctrl+左键已完成后，单次转移与整轮 `finally` 仍会产生额外鼠标释放。游戏会把脱离 Ctrl 的释放解释为普通左键动作，形成“受限物品被拿起，移动到第五个判空格后又被放下”的完整故障链。

## Goals / Non-Goals

**Goals:**

- 让清理操作只配对释放当前控制器真实持有的输入。
- 保证正常、异常、失焦和停止路径都保持鼠标先于修饰键释放。
- 用事件状态机复现受限物品及第五个判空格场景。

**Non-Goals:**

- 不定义或修改出库的点击后确认、重试次数和失败判定。
- 不增加输入时序配置、IPC 字段或用户设置。
- 不尝试自动移动、放回或恢复已经被游戏拿起的物品。

## Decisions

### 1. 显式跟踪控制器持有的输入

输入控制器在成功发送按下事件后登记键或按钮，并在配对释放的 `finally` 中移除登记。清理只遍历登记集合。相比查询全局按键状态后统一释放，这一方案不会干扰用户或其他输入源，也不会制造没有对应按下的鼠标释放事件。

### 2. 鼠标按钮先于修饰键清理

异常可能发生在鼠标按下与释放之间。清理必须先完成鼠标释放，再释放 Ctrl，保证残缺组合键仍保持 Ctrl+左键语义。正常动作已自行配对释放后，后续清理为空操作。

### 3. Ctrl 门禁作为独立防线保留

按下 Ctrl 并等待稳定后，通过 Windows 状态确认其已经生效；未生效时不发送左键。该门禁防止组合键本身退化，输入所有权跟踪则解决本次额外释放的根因，两者职责不同，不属于失败方案残留。

### 4. 不耦合出库确认策略

普通仓库和君锋镇可继续复用输入控制器，但它们如何确认来源格清空、是否重试以及重试次数由独立变更负责。本变更只保证每次底层 Ctrl+左键及其清理不会产生幽灵鼠标事件。

## Risks / Trade-offs

- [底层按下调用成功后进程被强制终止，来不及执行清理] → 保留现有进程停止机制；该极端情况不通过无条件释放补偿，因为补偿本身会制造错误点击。
- [测试只验证事件模型，无法替代真实游戏输入处理] → 在开发版使用类型受限仓库页复测，且不通过打包推进验证。
