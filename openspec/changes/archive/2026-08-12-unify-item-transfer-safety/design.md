## Context

普通仓库和君锋镇取件曾通过“图像变化且模型判空”确认转移，并允许第二次点击同一格。背包入库原先在点击前复制物品文本用于解析和黑名单判断，点击后直接继续；新增的点击后剪贴板确认又因游戏状态更新延迟造成三条路径中途停止。三条路径的候选识别目的不同，底层转移安全语义却不应分叉。

## Goals / Non-Goals

**Goals:**

- 让入库、普通仓库取件与君锋镇奖励取件复用同一份点击前剪贴板判空和单次点击实现。
- 确保同一来源格不会被自动点击第二次，也不会因点击后无法确认而停止整轮。
- 保持两个流程已有的候选识别、布局、黑名单和前台预检语义。
- 用行为测试和结构测试同时阻止后续实现再次分叉。

**Non-Goals:**

- 不统一入库与取件的候选生成算法。
- 不修改商城配方计划、断点或各取件场景的初始候选识别语义。
- 不检测单次点击后游戏是否实际完成转移；未转移的物品允许留在原位。
- 不执行安装包构建或发布验证。

## Decisions

### 1. 复用背包脚本的剪贴板输入控制器和共享单次转移函数

将点击前复制判空和 Ctrl+点击收敛到一个共享 Python 控制器。入库继续使用该控制器；普通仓库和君锋镇在模型生成候选后调用同一实现，不再自行组合键盘、鼠标、图像判空和重试。

选择该方案是因为入库已有剪贴板序列号、固定输入时序、前台门禁和完整释放逻辑。另建第二套剪贴板实现会继续产生漂移；直接让取件复用完整入库扫描流程又会错误耦合候选识别和黑名单。

### 2. 每个来源格只点击一次

调用方先取得点击前物品文本，共享函数只发送一次 Ctrl+左键。输入成功发出后直接处理下一目标，不再复制、截图或调用模型确认原格是否已清空。

不保留自动第二次点击。点击后确认无法可靠区分“点击未生效”和“点击已成功但游戏状态尚未更新”，会造成误停；允许偶发失败物品留在原地，比停止后续全部物品更符合批量存取目标。

### 3. 模型只负责候选，不负责转移确认

普通仓库和君锋镇都只使用高亮模型生成冻结候选。处理候选时移动到候选格并复制：复制为空说明该格已清空，直接跳过；复制到物品才执行共享单次转移。这样多格物品被取走后，其余占位格会自然判空，模型质量只影响初始“取哪些物品”。

### 4. 点击发出后提交统计

入库和取件在共享函数成功发出一次点击后增加处理数；入库同时根据点击前已经解析的物品登记多格占位。该统计表示已发送转移操作，不承诺游戏最终完成转移。

## Risks / Trade-offs

- [单次点击可能未实际完成转移] → 允许该物品留在原位并继续其他目标；不通过不可靠的点击后状态检查拖停整轮。
- [用户或其他程序同时修改剪贴板会影响点击前判空] → 点击前复制不可读时保持安全停止，空格则直接跳过且不点击。
- [共享控制器改动同时影响三条路径] → 为入库、普通取件与君锋镇取件运行同一组契约测试，并保留各自端到端测试。
- [君锋镇脚本与普通仓库共用入口] → 删除确认模式配置和分支，让两个入口执行唯一共享路径，避免后续再次漂移。

## Migration Plan

1. 先添加共享契约测试，分别复现普通仓库和君锋镇已转移但模型未判空、以及点击后确认误停的场景。
2. 提取共享单次转移函数并接入入库，确保点击前完成解析且点击后不复检。
3. 普通仓库与君锋镇统一改用共享函数，删除同格两次点击、图像判空确认、确认模式分支和本轮失败修复遗留测试。
4. 运行受影响测试、完整测试和 OpenSpec 严格校验；仅在开发版手动验证连续入库、普通取件与君锋镇取件。
5. 如需回滚，恢复两个调用点但保留单次点击禁令，避免重新引入重复点击风险。
