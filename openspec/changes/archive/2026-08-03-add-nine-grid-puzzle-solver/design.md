## Context

现有 Electron 应用已经具备全局快捷键、跨显示器物理区域选取、DPI 元数据、内置 Python 3.13 运行时以及 `cv2`、`mss`、`numpy`。新功能需要跨渲染层、主进程和 Python 识别脚本协作，但不应引入新的运行时依赖或自动输入行为。

## Goals / Non-Goals

**Goals:**
- 将视觉识别限制在用户配置的固定 6×10 区域，降低定位不确定性。
- 把识别和求解分离，使求解器完全确定、可单元测试。
- 保留每个识别格子的来源和置信度，以便修正后仍能给出取件位置。

**Non-Goals:**
- 不识别或覆盖左侧棋盘位置。
- 不自动点击、拖放碎片，也不创建游戏覆盖层。
- 不在本次变更中验证安装包。

## Decisions

### 使用四位接口掩码和有限枚举求解
每格使用 `N=1、E=2、S=4、W=8` 表示接口。九宫格内部只有 12 条无向边，先枚举其 4096 个组合并保留覆盖九个节点的 431 个连通子图；再按出口数从高到低枚举满足必选出口的 12 位边界掩码。内部边与边界位唯一确定九格掩码和五类用量，首次出现可行解的出口层就是全局最优层。

相比逐格启发式回溯，此方法最多检查约 176 万个组合，结果稳定、容易证明完备，并天然保证相邻接口成对出现。求解器统计全部最优布局数量，但只存储前 100 个去重布局。

### 识别使用固定网格和旋转模板匹配
Python 脚本按保存区域等分为 6×10 格，只截取每格上半部的符号子区。HSV 绿色掩码负责区分空格和符号，归一化后的掩码与五种基础模板的 90°旋转版本比较；最佳分数和候选分差共同决定置信度。

相比从整个屏幕自动寻找仓库，固定区域避免游戏装饰和其他绿色物品干扰；相比 OCR，拓扑模板不受物品等级文字和锁标记影响。模板保存在应用资源目录，脚本通过配置获得资源路径。

### 以可编辑格子作为库存真相
识别结果保存 60 个格子而不是只保存五个总数。用户修正格子后从格子重新派生数量，解决“手工增加数量却没有来源位置”的矛盾。来源选择按置信度降序、行列升序，人工修正格视为确定结果。

### 独立服务统一按钮与快捷键
主进程九宫格服务负责互斥、运行时解析、截图脚本生命周期和结构化错误。按钮与快捷键调用同一服务；识别脚本复用现有 Win32 窗口查找、恢复、置前和前台确认逻辑，成功激活游戏后立即截图，不使用固定倒计时。结果通过 `puzzle-analysis-updated` 推送，主窗口恢复并导航到 `/puzzle`。

区域配置保存物理矩形、显示器物理边界和缩放。分析前验证当前显示器环境与保存元数据兼容，避免在 DPI 或显示布局变化后截错区域。

## Risks / Trade-offs

- [游戏调整图标颜色或线条样式会降低模板置信度] → 所有低置信度格显式待确认，并允许逐格修正；模板和阈值集中管理。
- [用户框选边界不精确导致单元格偏移] → 使用每格相对中心子区并在测试中覆盖轻微偏移，配置页展示框选说明。
- [最优布局数量很大] → 继续统计总数但只保留前 100 个，使用紧凑的九字节掩码键去重。
- [Windows 拒绝游戏窗口置前] → 捕获前执行线程输入附加、恢复和置前并轮询确认；失败时不截图，恢复助手并给出结构化错误。

## Migration Plan

- 设置加载时通过默认值补入 `puzzleAnalyze: Alt+7` 和空的九宫格区域配置，不迁移旧数据。
- 变更可通过移除新路由、IPC、脚本与设置字段回滚，不影响现有模块数据。
