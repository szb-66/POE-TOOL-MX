## Context

见 [proposal.md](./proposal.md) 的动机。当前查价链路将固定交易目录、在线刷新、剪贴板解析、查价模型、主进程清理和官方请求序列化分开处理。目录目前能保留同文案多 ID，但模型不能表达“同一逻辑词缀的任一官方 ID”，因而把候选交给用户盲选。

当前腾讯国服固定数据按“相同 type + 完全相同官方中文文案”统计有 234 个重复组；这些组不能仅依赖固定国际服补丁数据，也不能通过运行时逐个搜索判断有效性。查询请求数、延迟和限流行为必须保持不变。

## Goals / Non-Goals

**Goals:**

- 让固定目录与在线刷新使用同一套确定性等价分组和版本化排除逻辑。
- 让逻辑词缀只向渲染层暴露一组可编辑边界，同时在主进程保留可信查询变体。
- 保持单 ID、综合词缀、负向 matcher、模型清理和重新查询的现有语义。

**Non-Goals:**

- 不在运行时向官方市集发送额外探测请求，不根据当前搜索结果自动学习排除清单。
- 不把本地别名命中、文案相似或只是数字数量相同视为等价。
- 不改变 IPC 通道、默认勾选策略、查询重试/限流或价格统计。
- 不打包、不发布，不对用户设置和本地数据做迁移。

## Decisions

### 1. 目录根节点保存等价组和版本化排除元数据

交易目录 schema 升级一版，增加两个根级集合：

- `statEquivalenceGroups`: 每项包含稳定的 group key、官方 type、标准化官方中文文案、数值占位签名和排序后的成员 ID。
- `unqueryableStats`: 每项包含 Provider、精确游戏版本、stat ID 和可审计原因。首条记录是腾讯国服 3.29 的 `implicit.stat_1571797746`。

等价组只由腾讯官方目录的原始 canonical text 生成，标准化仅统一 Unicode/空白和占位符表达，不应用业务别名、翻译补丁或模糊匹配。只有成员数大于一的组写入目录；group key 和成员使用固定排序，保证重新生成结果确定。

目录校验器要求每个成员 ID 实际存在且 namespace 与 type 一致，组成员的 canonical text 和占位签名一致；排除项必须指向存在的 ID，且 Provider、版本和原因均不得为空。排除项不从 stat 表中删除，因此覆盖审计仍能证明官方记录全部保留。

在线刷新在构建完本地化官方目录后，重新生成等价组并只应用精确匹配当前 Provider/版本的排除项，然后再执行现有原子切换。不得使用“小于等于版本”或默认继承规则。

**备选方案：** 把 `equivalenceGroup` 复制到每条 stat 或只维护手写 ID 对。前者使数据膨胀并增加不一致风险，后者不能覆盖当前 234 组和未来刷新，因此采用根级索引。

### 2. 先执行现有上下文消歧，后执行版本排除和等价收敛

解析器保留现有的词缀类型、物品类别、词缀元数据、local/global、多行文本和合并规则。完成这些缩小后，再从候选中移除当前 Provider/版本的不可查询 ID：

1. 剩余一个候选时，继续生成普通 stat。
2. 剩余多个候选时，只有它们全部属于同一目录等价组，且本次实际 matcher 的 type、捕获值个数和 `valueMultiplier` 都一致时，才生成一条逻辑 stat。
3. 其他多候选仍返回现有人工消歧模型。

逻辑 stat 使用等价组 key 作为合并身份，并保存一个按 ID 排序的内部 `queryVariants`；每个变体只含目录可重建的 ID、type 和 matcher 方向。本地显示值、来源引用和聚合只计算一次，不得因变体数量重复累加。

**备选方案：** 在上下文消歧前直接合并全部同文案 ID。这会隐藏本可以由物品类别或词缀来源确定的真实身份，所以等价组只是最后收敛步骤。

### 3. 渲染层编辑逻辑词缀，主进程重建可信变体

浮窗把含多变体的 stat 渲染为一行，沿用一个启用状态和一组最小/最大值，可以显示“已合并多个官方同文案过滤项”的非交互提示，不暴露 ID 选择按钮。

渲染进程返回的 `queryVariants`、等价组、type 和 `valueMultiplier` 均不可信。主进程模型清理先以已解析可信模型与当前目录定位逻辑 stat，再从目录组索引重建有效变体；旧模型中的无效 ID、额外成员和被篡改方向都会被丢弃。若可信组无法重建，该条件不得进入官方请求。

**备选方案：** 直接信任渲染层提交的变体。这会绕过现有 stat namespace 校验并允许恢复已排除 ID，不满足主进程信任边界。

### 4. 每个多变体逻辑词缀序列化为独立 `count/min=1` 组

查询序列化遍历启用后的逻辑 stat：

- 可信变体只有一个时，使用现有 `and` 组。
- 可信变体多于一个时，为该逻辑 stat 新建一个 `type: "count"` 组，设置组 `value.min=1`，并为每个变体写入一个 filter。

每个 filter 复用逻辑 stat 的显示 min/max，再通过该变体的可信 matcher 方向执行现有符号反转和边界交换。不同逻辑 stat 绝不共享 `count` 组，避免语义变成“任意一条词缀满足”。综合词缀和其他现有 filter group 保持原样。

本次胸甲中，排除 `implicit.stat_1571797746` 后只剩 `implicit.stat_2510655429`，因此它仍进入普通 `and` 组；该有效 matcher 方向为正，显示下界 50 序列化为 `min=50`，不生成 `max=-50`。

**备选方案：** 把所有等价变体放入一个全局 `count` 组，或分别放入 `and` 组。前者错误放宽多词缀查询，后者错误要求物品同时拥有所有等价 ID，因此使用每词缀独立分组。

## Risks / Trade-offs

- [官方同文案 ID 实际不完全等价] → 仅用 canonical 官方中文文案、type 和占位结构建组，解析时再要求本次 matcher 值个数和方向一致；不一致时保留人工消歧。
- [`count` 组增加官方查询复杂度] → 只在解析到并启用实际多变体词缀时生成，不展开未启用词缀，并保留现有查询过于复杂错误路由。
- [版本化排除清单过期] → 要求 Provider 和游戏版本精确匹配，新版本默认不继承；审计输出明示每条生效记录和原因。
- [目录 schema 升级导致旧快照不可用] → 同步更新固定快照、生成器、校验器和在线刷新回归；刷新失败时仍使用新 schema 的内置目录。
- [逻辑 stat 变体被重复计入聚合值] → `queryVariants` 仅作为查询传输元数据，合并、来源引用和综合计算均以逻辑 stat 为唯一单位。

## Migration Plan

1. 扩展目录 schema、生成器和审计，加入 3.29 首条版本化排除并重生成内置国服目录。
2. 实现解析收敛、逻辑模型、主进程可信重建和独立 `count` 组序列化，再接入浮窗单行展示。
3. 先运行目录/解析/查询/安全针对性回归，再运行完整 `npm test`、`npm run build`、OpenSpec 严格校验和 `git diff --check`。
4. 全部验证只在开发版进行，不执行打包或发布。

回滚时将目录 schema、内置快照和消费代码作为一个整体恢复；本变更不会写入用户数据，因此无需用户数据回滚。
