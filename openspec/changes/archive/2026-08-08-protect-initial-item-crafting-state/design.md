## Context

物品解析器与主进程结果已经提供 `isUnidentified` 和 `affixMatch`，设置中也已有 `wisdom` 坐标；缺口位于生成的制作脚本：首次结果被困在词缀模块内部且匹配发生在第一次通货消耗之后。制作启动门禁目前止于仓库选择和静态通货预检。

## Goals / Non-Goals

**Goals:**
- 以单一制作前准备流程服务全部物品制作模块。
- 复用同一份鉴定后解析结果完成首次词缀判断。
- 让准备阶段失败沿现有结构化启动错误链路传播。

**Non-Goals:**
- 不改变词缀组合匹配算法、稀有度预处理规则或可选成功收尾通货的语义。
- 不修改地图洗练已有的未鉴定处理，也不增加新的外部依赖。

## Decisions

1. `checkInitialItem` 存储在物品预设根级，并在现有快捷键和预设模块 `ModuleOne` 中编辑，不新增独立页面模块。规范化优先使用根级布尔值；缺失时默认开启，并兼容读取短期存在过的 `moduleTwo.checkInitialAffixes === false` 作为关闭值，随后不再向模块配置写回重复字段。
2. 物品脚本在静态通货预检后、发送 `crafting-startup-succeeded` 前调用统一准备函数。准备函数读取目标物品，必要时应用已经预检过的知识卷轴并重新读取，返回最终解析结果。相比在各模块重复鉴定，此方案保证只鉴定一次并覆盖仅插槽或仅古灵场景。
3. 物品制作静态通货清单始终把 `wisdom` 放在首位。虽然已鉴定物品不会实际消耗卷轴，但这保持“所有可能点击的固定通货必须在正式操作前预检”的现有安全约束。
4. `craft_affixes`、`craft_eldritch_implicits` 和 `craft_sockets` 都接收准备结果与同一个生成期页面开关。开启时分别检查 `affixMatch`、`eldritchImplicitMatch` 和 `socketMatch`；关闭时跳过首次命中分支，保留原先至少制作一次的行为。词缀首次命中和循环命中继续汇入同一成功收尾辅助逻辑。
5. 准备失败发送 `crafting-startup-failed`，并设置非零退出原因；沿用主进程已经监听的事件类型，避免新增 IPC 协议。

## Risks / Trade-offs

- [所有物品制作都要求知识卷轴坐标和库存] → 使用现有默认坐标、配置校验与名称预检给出明确错误，避免运行时误点。
- [模板字符串逻辑重复导致首次命中和循环命中行为漂移] → 抽取同一成功收尾代码路径，并用生成脚本行为测试覆盖两种入口。
- [相关文件存在未提交修改] → 只做小范围补丁，修改前后检查 diff，避免重写或格式化整个文件。

## Migration Plan

加载预设时通过既有规范化函数自动补齐默认开启值，无需一次性数据迁移。回滚代码后旧版本会忽略新增字段；不涉及持久化结构破坏。
