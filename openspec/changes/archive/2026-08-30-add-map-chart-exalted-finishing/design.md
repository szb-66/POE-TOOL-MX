## Context

见 `proposal.md`。地图与航海海图共用预设规范化和 `process_single_map` 状态机，但保存为独立预设。当前工作区正在把所有通货迁移到统一事务协议，协议已能用结构化 `detailedMods` 验证崇高石使词缀数增加；本变更必须复用该入口并保留未提交事务重构。

## Goals / Non-Goals

**Goals:**

- 在每份稀有候选的首次条件判断前完成固定六词缀补满。
- 让每颗崇高石分别确认，失败时保持当前格和现有恢复边界。
- 让旧预设保持原行为，并让地图/海图开关继续相互隔离。

**Non-Goals:**

- 不提供可配置的目标词缀数量，不改变数值和黑白名单算法。
- 不改变已腐化、传奇、不可修改对象的既有策略。
- 不新增事务协议、公开 Electron API、依赖、打包或发布步骤。

## Decisions

### 1. 预设使用与瓦尔同形的独立开关

在公共洗练配置中保存 `exalted: { enabled: false }`，迁移时与默认值合并。相比复用装备制作的 `enableExalted`，独立对象能保持地图领域结构一致并让地图、海图预设自然隔离。

### 2. 以结构化前后缀计数作为唯一补满依据

补满逻辑调用共享 `_explicit_affix_count`，只接受 `detailedMods` 中的 prefix/suffix；不按 `explicitMods` 文本行数猜测，因为一个词缀可能包含多行。计数缺失或越界时在使用下一颗通货前失败关闭。

### 3. 在稀有候选条件判断前设置统一补满门禁

状态机在任何 `check_map_base` 或 `check_map_mods` 之前先检查稀有候选并补满。点金模式失败后重铸、混沌模式失败后重骰；各自生成的下一份稀有候选重新经过同一门禁。相比只在既有“已满足”分支收尾，此设计保证新增词缀参与全部属性和词缀条件。

### 4. 每颗崇高石复用现有事务

循环每次调用一次 `apply_currency_and_read("exalted", ...)`，已确认快照成为下一次动作前快照。事务负责单次输入、结构迁移、账单和发布确认；领域循环只负责上限六和下一步策略，避免重复确认逻辑。

## Risks / Trade-offs

- [补满会消耗崇高石后才发现候选不达标] → 这是明确的产品顺序；界面开关默认关闭，只有用户主动启用才执行。
- [详细词缀格式随游戏补丁变化] → 复用现有未适配检测并安全停止，不退回文本行数猜测。
- [与事务重构编辑同一模板] → 只在当前事务入口周围增加领域门禁，并用针对生成后脚本的回归测试证明没有旁路。

## Migration Plan

旧地图和海图预设加载时补入关闭的开关；回滚代码后多余字段会被既有配置清理忽略。开发版依次运行定向测试、完整测试、构建和 OpenSpec 严格校验，不执行打包或发布。
