## Context

参见 [proposal.md](proposal.md) 的问题说明。`bag_auto_stash_template.py` 的 `_copy_item_text_once` 与 `chaos_recipe_pick_template.py` 的 `copy_item` 存在与已修复的装备/地图模板相同的缺陷：复制成功判定不要求剪贴板内容实际变化，游戏复制失败时残留的旧物品文本会被当作当前复制结果。

`bag_auto_stash_template.py` 的空格扫描依赖快速路径：空格格复制后剪贴板变空即判定，不重复确认以保持扫描速度。修复必须保留该路径，不能简单退化为一律等待超时。

## Goals / Non-Goals

**Goals:**

- 残留旧文本在任何复制确认路径中都不再被判定为「复制到物品」。
- 保持 bag 存仓空格扫描的快速判定路径（剪贴板变空且序列号变化即空格）。
- 商城配方取件在复制失败时重试，不再把残留旧文本当作移动结果。

**Non-Goals:**

- 不改变存仓/取件的点击次数、重试上限、时序配置与前台门禁。
- 不修改已修复的装备/地图模板逻辑。
- 不引入新依赖或共享模块抽取。

## Decisions

### 1. bag/君锋 `_copy_item_text_once`：内容双验证 + 保留空格快速路径

按以下判定顺序实现：
- 序列号与内容双条件都满足（内容非空且 ≠ 复制前文本）→ `"copied"`。
- 剪贴板内容为空且序列号确实变化过 → `"empty"`（空格快速路径，保持原扫描速度）。
- 其余情况（含残留旧文本：内容 == 复制前文本）→ 继续轮询直至超时 → `"no-response"`。

序列号不可用时回退：内容非空且 ≠ 复制前 → `"copied"`；内容为空 → 继续等待至超时（与原逻辑一致，`"no-response"` → 上层重试后判空格）。

备选方案是把残留旧文本直接判 `"empty"`。这会误判「物品仍在但复制失败」的场景（取件确认会把未移走的物品当已移走），因此不采用；`"no-response"` 让上层按既有重试语义处理。

### 2. 商城配方取件无需修改

`chaos_recipe_pick_template.py` 的 `copy_item` 在发送 Ctrl+C 前执行 `pyperclip.copy("")` 清空剪贴板，复制失败时剪贴板为空而非残留旧文本，不存在同款「旧文本被当作复制结果」问题。其 after 复制为空时无法与「复制失败」在剪贴板层面区分，属既有固有不确定性，不在本次修复范围。

备选方案是为 `copy_item` 增加 before 对比与失败信号。经核实清空机制已消除残留旧文本路径，新增信号无收益且改变既有取件判定语义，因此不采用。

## Risks / Trade-offs

- [残留旧文本场景多等待一个轮询周期] → 超时窗口沿用现有 `clipboard_delay`，不增加等待上限。
- [bag 空格快速路径依赖序列号可用] → 序列号不可用时回退到内容对比，行为与原逻辑一致，仅空格判定路径变化。
- [君锋复用同一控制器] → 同一函数修复同时生效，junfeng 测试回归确认。

## Migration Plan

1. 先添加失败复现测试：残留旧文本不判 `"copied"`、空格快速路径保留。
2. 修改 `bag_auto_stash_template.py` 的 `_copy_item_text_once`。
3. 确认商城配方取件清空机制已消除同类路径，无需修改。
4. 运行 `bagAutoStash`、`junfengHighlight` 定向测试与全量 `npm test`。
5. 回滚可整体撤销 `_copy_item_text_once` 验证改动；不迁移持久数据或用户预设。
