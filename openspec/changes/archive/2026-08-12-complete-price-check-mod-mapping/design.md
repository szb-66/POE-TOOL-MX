## Context

参见 `proposal.md` 的问题背景。当前流程由物品解析器生成结构化词缀，`catalog.js` 把官方 stats/items 转成运行时目录，`query.js` 按正规化文本和类型查找单个 ID，服务再构造官方查询并推送浮窗。

现有反馈环证明了三个根因：目录构建按显示文本聚合后会删除同类型多 ID 候选；匹配器在目标类型缺失时回退到 explicit ID；解析器没有把游戏复制文本中的类型元数据作为最高优先级，普通 `(fractured)` 行被当作显式文本，详细复制的 `Fractured Prefix/Suffix Modifier` 又会被前后缀字样抢先归类为 explicit。内置目录只有 6 条 stat，导致官方刷新不可用时覆盖几乎归零。当前仍在维护的国际服实现会先按本地化类型关键字恢复类型，再做 stat 匹配；游戏语义和 ID 跨服务器通用，国服差异只应停留在翻译与接口适配层。

## Goals / Non-Goals

**Goals:**

- 让目录数据模型无损表达官方记录与歧义，而不是在构建阶段强行压成单 ID。
- 建立确定性的解析、消歧、合并和用户候选闭环；任何路径都不猜 stat ID。
- 从普通复制尾标和详细复制元数据自动恢复真实词缀类型，不把类型判断转嫁给用户。
- 让完整内置目录、运行时刷新和覆盖审计使用同一 schema 与验证器。
- 分离国际服通用语义与国服本地化 matcher，避免用停更项目的数据版本定义游戏规则。
- 复用现有解析器、查询模型、服务和浮窗，不建立第二套查价链路。

**Non-Goals:**

- 不替代腾讯官方搜索、挂单和限流接口。
- 不用机器学习或基于搜索结果数量猜测正确 stat；零挂单不能证明映射错误。
- 不在本变更中实现市场估值模型、自动议价或批量仓库估值。
- 不执行安装包验证；仅在开发版验证，若后续必须打包则先取得用户确认。

## Decisions

### 1. 目录 schema 升级为无损候选记录

每条官方 stat ID 保持独立稳定记录，并保存类型、matcher、显示标签及可用的类别/解析元数据；索引由“matcher → 单条记录”改为“正规化 matcher → 候选数组”。相同 matcher 合法重复，唯一性校验转到记录键和“类型 + stat ID”。运行时官方刷新与内置快照都经过同一个验证和覆盖报告。

选择该方案是因为歧义属于真实数据，构建时删除或任取一个都会造成漏查/错查。备选方案“同文案只留第一个 ID”被拒绝，因为顺序不具备业务语义；“继续按文本聚合但保存 ID 数组”不足以表达候选各自的上下文和合并策略。

### 2. 先恢复游戏声明的词缀类型，再执行单一分阶段解析器

解析器沿用当前 `createPriceCheckModel` 入口，对每个结构化 modifier 执行以下阶段：

1. 识别普通复制的 `(implicit)`、`(fractured)`、`(crafted)`、`(enchant)` 等稳定尾标；识别详细复制元数据中的本地化类型关键字。破碎、工艺等语义类型优先于 Prefix/Suffix 位置，并另存前后缀位置供消歧。
2. 移除不影响 stat 身份的官方尾注并保留原文。
3. 按最长完整多行优先尝试，失败后再逐行推进，避免先匹配短行拆散复合词缀。
4. 把数值转换为受限占位组合；优先全部可变值，再尝试保留部分固定值，最后才尝试精确原文。组合数设置硬上限以防指数增长。
5. 仅保留与 modifier 类型相同的候选；不得回退 explicit。
6. 使用物品类别、完整文本、词缀名称/标签和目录 resolver 规则消歧。
7. 唯一候选生成 stat；可合并组按声明规则聚合；其余保留为 ambiguity。

这复用现有模型和调用方，符合最小改动原则。备选方案是在 UI 中对每行直接搜索整个目录，会重复解析逻辑且难以测试，因此不采用。

### 3. resolver 规则是数据，不是散落条件分支

目录记录允许声明少量可审计策略：按物品类别选择、同语义平凡合并、百分比/固定值合并和标志值合并。生成器保存源数据提供的 resolver 元数据；官方实时目录缺少上下文时只补充/更新 ID 与文案，不覆盖内置 resolver。无法由数据证明的情况保持候选状态。

备选方案是在代码中为每个已知词缀写特例，短期容易但会随赛季积累且无法量化覆盖，因此拒绝。

### 4. 歧义成为一等查询模型状态

查价模型为未决词缀保留稳定 key、原文、类型、数值、原因和候选；候选包含 stat ID、区分标签与适用上下文。模型清理器只接受当前服务端目录中存在且类型匹配的候选 ID，防止渲染层注入任意过滤条件。

浮窗把“未映射”改为可展开项：若有候选，用户可选择后转为普通过滤项并在原位置重新查询；也可保持排除并继续。没有官方候选的说明文本继续只读展示。选择仅作用于当前捕获，避免把一次人工判断永久应用到不同物品类别。

### 5. 国际服通用语义与国服本地化分层，官方刷新原子增强

生成脚本把国际服官方目录作为当前通用 ID、类型和查询语义来源，再按相同 ID 覆盖腾讯国服 matcher 与物品名称；历史国服项目的数据只能作为翻译兜底，元数据必须记录其实际版本，不能因快照在今天生成就宣称内容是当前版本。启动时加载并验证内置快照，随后并行刷新国服官方 stats/items。只有两个响应和新目录全部通过验证后才原子替换，失败则保留内置/最近成功目录并发布可重试状态。

不采用“启动时只有 6 条、等待网络补齐”，因为查价快捷键在窗口显示后立即可用。也不把官方响应持久化到包含账号信息的位置；目录本身是公共元数据，诊断不得记录 Session 或请求头。

### 6. 覆盖审计与真实语料共同作为完成门槛

覆盖审计对输入官方响应逐条分类为：保留且唯一、保留但歧义、等待本地化、明确不支持类型/无效记录；任何无分类消失都失败，并额外比较国际服通用 ID 与国服本地化 ID。测试加入普通 `(fractured)`、详细 `Fractured Prefix/Suffix Modifier`、本地化破裂/破碎关键字、既有两个根因夹具、数字占位、多行、类别 resolver、合并、候选选择、目录降级和模型清理。

真实语料使用脱敏的国服剪贴板文本，仅包含物品公开描述，不包含账号、Cookie、用户路径或挂单私有信息。开发版端到端验证通过游戏快捷键捕获、浮窗选择/跳过、重新查询和官方页面跳转；若当前机器无法访问官方目录，允许使用保存的官方响应夹具验证覆盖审计，但必须如实记录实时探针失败。

## Risks / Trade-offs

- [内置目录会随赛季过期] → 通用语义从当前国际服官方目录更新，国服快照单独保存来源版本/时间，并在开发流程中提供刷新与严格 ID 差异检查；运行时仍用国服官方目录原子增强。
- [国服翻译更新晚于通用数据] → 保留新 ID 和真实类型，将其标记为等待本地化；取得腾讯目录后按 ID 补齐，绝不退回错误类型。
- [数字占位组合造成匹配量膨胀] → 限制可处理数字数量与组合上限，使用正规化索引先缩小候选。
- [官方实时目录缺少类别消歧元数据] → 合并内置 resolver；仍不唯一时交给用户，不猜测。
- [人工候选标签可能难以区分] → 优先展示类别/来源/官方标签；确无可读差异时显示类型与短 stat 标识并保留官方页路径。
- [完整内置目录增大仓库和应用体积] → 只保存查价所需字段，不引入原始数据或运行时依赖。
- [现有用户提交的旧模型不包含候选结构] → 清理器向后兼容旧字段，所有 stat ID 仍由主进程目录白名单验证。

## Migration Plan

1. 先升级 schema、生成器和验证器，拆分通用语义来源与国服本地化来源，并生成来源时间真实可追踪的内置快照。
2. 在解析入口恢复普通/详细复制中的真实类型，再引入候选索引与解析 resolver，保持现有查询输出字段兼容。
3. 扩展模型/IPC/浮窗处理真正的 stat 歧义并完成安全清理；类型已明确时不显示人工类型选择。
4. 使用国际服/国服 ID 差异审计、当前格式与真实国服语料、查价测试全集、Vite 开发转换和 `npm test` 验证。
5. 回滚时恢复旧目录 schema、解析器和浮窗字段；不涉及用户数据迁移，现有查价设置保持不变。
