## Context

主窗口当前在窗口管理模块内直接处理刷新快捷键：普通刷新调用页面重载，强制刷新调用忽略缓存的页面重载。应用主进程已经拥有统一的异步资源清理和退出控制，但该控制器面向“退出”，不会区分清理成功与失败后是否允许重启。开发入口由一个父 Node 进程同时管理 Vite 服务和单个 Electron 子进程；若 Electron 自行 `relaunch`，父进程会在旧子进程退出时关闭 Vite，导致新实例失去页面服务。

本设计遵循 [proposal.md](./proposal.md) 和 [application-force-refresh spec](./specs/application-force-refresh/spec.md) 的行为约束，并以开发版验证为准。

## Goals / Non-Goals

**Goals:**

- 将窗口快捷键识别与应用生命周期动作解耦，由主进程决定如何执行完整重启。
- 在新实例启动前获得明确的“清理与缓存失效成功”结果。
- 为正式版和开发版提供不同的进程拉起机制，但保持同一用户行为。
- 保证重复触发只共享一个正在进行的重启操作。

**Non-Goals:**

- 不改变关闭窗口、应用更新安装或启动崩溃恢复的现有行为。
- 不清除 Cookie、Local Storage、用户配置或业务数据。
- 不让普通刷新重启主进程，也不新增菜单、按钮或公开 IPC。
- 本变更不执行打包或正式版发布验证。

## Decisions

### 1. 窗口管理器通过回调请求强制刷新

`createMainWindow` 接收主进程提供的强制刷新回调。窗口模块继续负责把键盘输入判定为 `reload` 或 `force-reload`，但 `force-reload` 不再直接操作 `webContents`，而是调用回调；普通刷新仍直接重载页面。

这样窗口模块无需导入 Electron `app` 或了解清理、开发模式和重启策略。备选方案是在窗口模块直接调用 `app.relaunch()`，但会绕过统一清理，也无法正确协调开发服务器，因此不采用。

### 2. 使用独立且幂等的应用重启协调器

新增生命周期层的重启协调器，接收以下依赖：统一资源清理、主窗口会话缓存清理、成功后的进程重启动作、失败记录和失败后的终止动作。协调器缓存首次请求产生的 Promise，后续请求复用该 Promise。

重启准备顺序为：

1. 进入 restarting 状态并拒绝创建第二个流程。
2. 在既有退出时限内执行统一资源清理。
3. 清除主窗口所属 Session 的 HTTP/页面缓存。
4. 将既有退出控制器标记为已完成清理。
5. 根据运行模式执行正式版重新拉起或开发版重启信号。

任何清理或缓存失效失败都记录根因并执行不拉起新实例的终止动作。备选方案是先调用 `app.relaunch()` 再清理，但 Electron 会保证计划拉起，无法在清理失败后撤销，可能让遗留自动化进程与新实例并发，因此不采用。

### 3. 正式版在准备成功后使用 Electron relaunch

正式版准备成功后先调用 `app.relaunch()`，再结束当前实例。由于统一资源清理已经完成，退出控制器需处于 ready 状态，避免 `before-quit` 重复清理。跨进程实例锁也在新实例启动前释放。

失败路径不调用 `app.relaunch()`，当前实例以失败状态退出。这样优先保证不会出现两个可能同时执行自动化的应用实例。

### 4. 开发版通过专用退出码让父进程重新拉起 Electron

开发版不调用 `app.relaunch()`。准备成功后 Electron 使用专用、集中定义的退出码结束；`scripts/dev.js` 将单次 spawn 改为受控循环：收到该退出码时保留 Vite 服务并创建新的 Electron 子进程，收到其他退出码时关闭 Vite 并结束。

该循环始终只跟踪一个 Electron 子进程，因此后续正常退出能够正确回收 Vite。备选方案是让旧 Electron 自行 relaunch 并要求父进程永久保留 Vite，但父进程将失去对新子进程的生命周期跟踪，容易遗留开发服务器，因此不采用。

### 5. 只清除页面缓存，不清除持久化存储

重启协调器调用主窗口 WebContents 所属 Session 的缓存清理能力。该操作限定于 HTTP/页面缓存，不调用 Session 数据清理、Cookie 清理或应用数据目录删除，从而延续原 `reloadIgnoringCache` 的意图并保留登录和用户配置。

缓存清理必须在旧主窗口仍可访问时完成；统一资源清理不得提前销毁主窗口。现有清理流程仅销毁辅助窗口，符合该约束。

## Risks / Trade-offs

- [清理失败导致应用退出但没有自动恢复] → 记录明确失败原因，并以“不启动可能重叠的新实例”为安全优先；用户可在确认旧进程结束后手动启动。
- [专用退出码与普通故障退出码冲突] → 在共享的纯常量模块中集中定义并为开发启动循环添加测试，仅在重启准备成功路径使用。
- [重复快捷键在窗口关闭前继续到达] → 重启协调器共享同一个 Promise，窗口层不自行创建重启过程。
- [缓存清理扩大到登录或业务数据] → 仅调用 Session 的 cache API，并通过测试确认未调用 storage/cookie 清理接口。
- [修改开发启动器后异常退出无法回收 Vite] → spawn 循环对非重启退出码和子进程启动错误统一进入 finally 清理服务器。

## Migration Plan

1. 先增加重启协调器和开发启动循环的单元测试，再接入主窗口快捷键。
2. 在开发版验证普通刷新不重启、强制刷新后 Electron PID 改变且 Vite PID 保持、第二次正常退出能够关闭 Vite。
3. 运行受影响测试、完整 `npm test` 和 OpenSpec 严格校验；不执行打包。
4. 若需回滚，恢复窗口模块的 `reloadIgnoringCache()` 调用并移除未再引用的重启协调器、退出码与开发 spawn 循环，保留既有退出清理逻辑不变。
