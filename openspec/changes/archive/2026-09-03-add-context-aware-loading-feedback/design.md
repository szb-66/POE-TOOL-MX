## Context

现有路由遮罩、按钮 loading、制作/查价浮层与海图识别反馈分别管理状态。游戏前台监视器能识别可信游戏，但只发布布尔状态；浮士德与海图各自持有识别反馈窗口。新机制需要跨 renderer、主进程和 Python 子进程生命周期工作，同时不得削弱现有前台输入安全门禁。

## Goals / Non-Goals

**Goals:**
- 用单一生命周期模型填补“用户触发到首个业务反馈”的空档。
- 由业务固定声明 app/game 目标，并用真实前台状态控制显隐。
- 复用现有游戏反馈视觉和进度能力，避免重复浮层。

**Non-Goals:**
- 不拦截所有 IPC 或 Promise，不为短请求增加反馈。
- 不替换业务结果、错误、取消或持续运行状态。
- 不在本次变更中打包或发布。

## Decisions

### 使用主进程令牌协调器与静态操作目录
主进程是窗口焦点、游戏边界和业务子进程的共同可信边界。目录将 renderer 可请求的 operationId 映射到固定目标和文案，renderer 只得到不透明令牌。相比全局拦截 IPC，该方案不会错误标记后台同步或重复已有反馈。

协调器按 `priority`、开始序号选择同目标的主操作，执行显示延迟和最短可见时间。`finish` 幂等；sender 销毁和应用清理按所有者批量结束。

### 用一个共享快照驱动应用组件和游戏窗口
协调器发布仅含 `visible/target/label/current/total/activeCount` 的规范化快照。应用根布局渲染 app 快照；现有识别反馈窗口演进为共享游戏反馈窗口并渲染 game 快照。业务提供真实进度时显示进度，否则只显示旋转状态。

### 目标固定，焦点与业务阶段共同决定开始和显隐
操作登记后不随焦点迁移。游戏目标在激活完成且可信游戏前台时出现；app 目标只在主窗口聚焦时出现；其他焦点一律隐藏。对于浮士德“开始改价”，窗口激活是瞬时前置动作，不属于长加载：主进程必须先确认游戏聚焦，再创建准备令牌并开始延迟计时。这样提示只覆盖游戏内专用识别浮层首次加载的空档，不会在激活游戏前错误显示于应用，也不会覆盖浏览器。

### 前台监视器补充物理边界
Windows watcher 对可信游戏窗口读取边界并将边界变化纳入状态变化判断。主进程保留原始身份信息，只把边界用于定位不可聚焦的游戏反馈窗口。坐标使用现有物理/DIP 转换函数，窗口顶部居中并限制在目标边界内。

### 以真实可见反馈交接而非 IPC 返回交接
需要加载模型的 start IPC 通常在子进程创建后立即返回，因此准备令牌由 manager 持有。若已有专用业务浮层，只有该浮层完成页面加载、实际显示后才能立即交接；仅创建窗口或调用 `showRunning` 不算可见反馈。没有专用浮层的流程则保持到 `started/scan-plan/progress/result/error` 等首个业务事件。一次性预览在 Promise 完成的 finally 中结束。

## Risks / Trade-offs

- [watcher 250ms 轮询会造成短暂显隐延迟] → 保持提示非交互，并在激活结果可用时立即刷新状态。
- [专用浮层首次加载可能持续数秒] → 以浮层实际显示回调作为交接点，统一提示在此之前持续展示。
- [遗漏 finish 导致残留] → 所有接入点使用 finally、子进程 error/close 和 cleanup 三层清理，并测试重复结束。
- [当前工作区已有反馈相关改动] → 在现有识别反馈管理器上增量抽象，不回退或覆盖窗口激活改造。
- [多个游戏自动化同时请求反馈] → 沿用自动化锁，同时协调器仍按优先级确定唯一展示。

## Migration Plan

先加入协调器、静态目录和共享渲染，再逐项迁移浮士德/海图并接入缺失流程。每项接入均保留原业务状态和错误处理；若回滚，可移除接入调用并恢复各 manager 对现有反馈管理器的直接使用，不涉及持久数据迁移。
