## Context

自动喝药 Python 进程目前只在启动时读取 JSON；背包模块虽已有若干增量 IPC，但页面仍锁定布局和黑名单，且多个 store 以 fire-and-forget 方式同步。公共界面检测协调器已具备配置变化重启能力，仓库取件、商店配方和查价也已有运行时更新入口，可在现有架构上统一提交语义。

## Goals / Non-Goals

**Goals:**
- 让持续运行功能在保持开启状态下可靠应用有效配置。
- 明确检测配置立即生效、输入动作配置下一轮生效的安全边界。
- 保证界面、持久化配置和主进程最后有效配置一致。

**Non-Goals:**
- 不让物品制作或洗图在单次任务中途换配置。
- 不修改现有 localStorage 数据结构，不中断当前鼠标键盘动作以追求即时切换。

## Decisions

1. **自动喝药使用原子 JSON 文件和修订号热加载。** 主进程持有最后有效配置与修订，规范化、校验后以临时文件替换；Python 在检测循环边界按文件修改时间读取，失败时保留内存缓存。相比重启子进程，这能保留运行状态和统计且没有输入中断窗口。
2. **背包使用单一完整运行时更新入口。** renderer 构建与启动时相同的规范化配置，主进程验证后替换 `latestConfig`；检测指纹变化才调用协调器重载，动作字段只由下一次 `startStashProcess` 快照。相比继续扩展字段级 IPC，可避免遗漏和部分更新。
3. **store 串行提交候选副本。** 每个持续功能维护最后成功快照和本地修订队列；只有 IPC 成功才保存，失败恢复快照。组件不直接把尚未验证的深层变更当作已生效状态。
4. **复用既有运行时通道。** 仓库取件、商店配方、查价不新增主进程协议，只在 store 层统一排队、修订和错误传播，当前自动化仍持有启动请求快照。

## Risks / Trade-offs

- [检测模板变化会短暂重启公共检测进程] → 保留消费者集合并发布 `reloading`，不把主动重载报告为异常。
- [连续快速编辑造成异步响应乱序] → 同一模块更新串行化并只接受最新修订。
- [Python 读取到临时或损坏文件] → 原子替换并在解析失败时继续使用最后有效内存配置。
- [当前动作与页面新值短暂不同] → 明确标注“当前轮保持原配置，下一轮生效”，不修改执行中的输入快照。

## Migration Plan

无需数据迁移。旧设置仍由现有 normalize 函数补全；新增 IPC 不改变旧启动接口。出现问题时可停止对应功能，旧的启动时配置路径仍可重新建立有效运行态。
